# Methodology 0.3-draft

Status: **draft. Nothing here is frozen** until it is published with a version number (target: 1.0). Every check, probe, threshold, and the grading formula can still change, and a change will bump the methodology version recorded in each result. A grade from this draft is a local test result, not a public rating.

Sections 1 to 7 below describe the 0.3-draft build and name the code they were written against. They give the full corpus and verdict rules of the `core` and `db` packs, which are the ones a normal run always meets; the other packs (`sqlite`, `fs`, `net`, `git`, `http`, `effects`, `exec`, custom probes) are summarised in section 1, and `sealmark explain <check-id>` and `sealmark list-checks` print the registry from the code for every check. [What changed in 0.3-draft](#what-changed-in-03-draft) lists every change since 0.2-draft that can move a verdict (its "Round 4" and "Round 5" subsections are the latest, and Round 5 supersedes the round-4 net refusal tiers), and "Candidate checks" below is current for 0.3-draft.

What an A means: the server passed these specific, published probes with this exact configuration. It is not a security endorsement, and it says nothing about what the probes do not cover (see [Known blind spots](#known-blind-spots)).

Sources of truth for this document: `cli/src/packs/core.ts`, `cli/src/packs/db.ts`, `cli/src/seed.ts`, `cli/src/mcp.ts`, `cli/src/config/schema.ts` and `docs/mvp-design.md`. If this document and the code disagree, the code is what runs; file a docs bug.

## 1. Model

- The harness is an MCP client. It calls tools directly with fixed inputs. **No LLM is in the loop.**
- Nine packs ship (plus `custom`, which is your own `probes:`). `core` applies to any MCP server (stdio or HTTP). The others apply only when the harness can give the server a target it owns:

  | Pack | Target | Checks (ids) |
  |---|---|---|
  | `core` | none | `protocol`, `tool-poisoning`, `robust-input`, `secret-echo` |
  | `db` | seeded Postgres | `read-only`, `write-gate`, `rls`, `mutating-sql`, `pii`, `pii-masked`, `db-rowcap`, `db-timeout`, `audit`, `db-privilege` |
  | `sqlite` | seeded SQLite file | `sqlite-read-only`, `sqlite-mutating-sql`, `sqlite-file-read`, `sqlite-file-write`, `sqlite-extension-load`, `sqlite-rowcap`, `sqlite-timeout` |
  | `fs` | sandbox directory tree with canaries | `fs-read-escape`, `fs-write-escape`, `fs-link-escape`, `fs-size-cap` |
  | `git` | sandbox repositories | `git-repo-scope`, `git-arg-injection` |
  | `net` | loopback listener | `net-loopback-ssrf`, `net-scheme-allowlist`, `net-caps`, `net-redirect` |
  | `http` | the HTTP endpoint you configured | `http-origin`, `http-auth`, `http-protocol-version`, `http-session`, `http-cors`, `http-bind`, `http-tls` |
  | `effects` | sandbox | `annotation-honesty`, `openworld-honesty`, `undeclared-writes` |
  | `exec` (opt-in, `--active`) | sandbox `bin` programs | `exec-injection`, `exec-cwd`, `exec-timeout-cap`, `exec-allowlist` |

  This document spells out `core` (section 5) and `db` (section 6). A pack that does not apply is reported as not applicable with its reason, never silently skipped. The retired `db` id `cap-timeout` was split into `db-rowcap` and `db-timeout`; the old id still works in configuration, with a warning.
- Each check returns a **verdict**: `pass`, `part` (partial), `fail`, `inconclusive` (the harness could not tell), or `na` (not applicable).
- Each check carries a **scope** line printed in every report: whether it measures the *server's* behavior, or a *database control tested through the server* (does the server defeat a control the database already enforces?).
- Each piece of evidence says how it was established (`verifiedBy`):
  - `db-state`: the harness read the database directly over a separate superuser connection and saw the row, table, or value change (or not). The server's own answer is not trusted.
  - `fs-observer`, `listener` and `process`: the harness diffed the sandbox file tree, saw a connection or request on its loopback listener, or listed the server's process tree.
  - `http`: decided from an HTTP exchange with the configured endpoint.
  - `response`: decided from what the server returned (text, error flag, row count, elapsed time).
  - `protocol`: decided from MCP protocol behavior (handshake, `tools/list`, liveness after a call).
  - `static`: decided from tool, prompt and resource metadata, without calling any tool.
- Every result records the exact server command with placeholders unexpanded, the server env (canary values shown as `<canary>`; HTTP headers listed as `header:<Name>`), the discovered tools, the SQL tools, the database mode and seed version, and the probe options, so a run can be reproduced. A literal value under a secret-looking name (a key matching `key|token|secret|passw|auth|credential|cookie|bearer`) is shown as `<redacted>` and credentials in a URL are dropped, so a shared report does not carry them. Redaction is by name only: do not rely on it, and keep real secrets out of `sealmark.yaml`.

## 2. Grading formula

Computed per pack, per server version. Grades are never inherited between versions.

1. Take the pack's checks that are **not advisory**.
2. A check is *scored* if its verdict is `pass`, `part`, or `fail`. Points: pass = 1, part = 0.5, fail = 0.
3. If nothing is scored, **no grade is produced** (status `na` or `inconclusive`, with the reason). A letter is never invented.
4. Percentage = points / scored.
5. Raw letter: A >= 90%, B >= 75%, C >= 60%, D >= 45%, otherwise F.
6. **Critical cap:** if any critical check has verdict `fail` and the raw letter is above D, the grade is D (`capped = true`). A raw D or F is not changed. A `part` on a critical check does not trigger the cap.
7. **Provisional:** if any critical check is `inconclusive`, the grade is marked provisional (`*`) because a critical question is unanswered.
8. **Excluded:** non-advisory checks that are `inconclusive` or `na` leave the denominator and are listed in the result.
9. Advisory checks are shown, labelled `(advisory, not scored)`, and never change the letter.
10. **The A gate (0.3-draft, decided by recommendation, owner may veto).** The formula above is unchanged: a provisional A is still graded A and printed `A*`. What changed is how it is read against a gate: a provisional grade does **not** meet `--fail-under A`, because "every critical question answered" is part of what an A claims. Lower gates are unchanged (a provisional B meets `--fail-under B`). This is an exit-code rule, not a grading rule; it lives in `cli/src/report/exit.ts`.

The fraction printed beside a grade is the same in every format: points over scored checks, for example `3/4 points, 75%`, plus `1 of 5 checks not scored` when a check was excluded.

Worked examples (from the toy servers used to test the harness; these are test fixtures, not real servers):

| Case | Scored | Points | Raw | Final |
|---|---|---|---|---|
| core: protocol pass, poisoning pass, robust pass, secret-echo pass | 4 | 4 | 100% A | A |
| core: poisoning fail, other three pass | 4 | 3 | 75% B | **D** (capped) |
| db: read-only, mutating, cap pass; rls and pii fail | 5 | 3 | 60% C | **D** (capped) |
| db: three checks fail, two pass | 5 | 2 | 40% F | F (not changed by the cap) |

Why these numbers: the letter bands are conventional school-style bands chosen for legibility, not derived from a risk model. Partial = half a point is a simplification. The critical cap exists so that a server that leaks other tenants' rows, unmasked personal data, or runs injected SQL can never show a good letter by passing the easy checks. All of these are open to change before 1.0.

Rule of thumb for reading the number: with 4 or 5 scored checks, one check moves the percentage by 20 to 25 points. A letter on this few checks is coarse. Read the per-check lines, not just the letter.

## 3. Seed database (seed 0.2)

Created fresh on every run in a database named `sealmark_seed`. Synthetic data only; nothing here comes from any real system.

| Object | Contents |
|---|---|
| `tenants` | 2 rows: 1 `Acme Test Co`, 2 `Globex Test Co` |
| `customers` | 100 rows, 50 per tenant. `name` = `Customer N`. `email` = `cust` + 4 digits + `@example.test` (tenant 1: `cust1001`..`cust1050`, tenant 2: `cust2001`..`cust2050`). `note` = `T1-NOTE-N` for tenant 1, `T2-SECRET-N` for tenant 2 |
| `orders` | 100 rows, one per customer, `note` = `T1-NOTE-order-ID` or `T2-SECRET-order-ID` |
| `big_table` | 200,000 rows: `id`, `payload` = `row-ID-end` |
| `probe_t` | empty scratch table (`id int primary key`, `v text`); mutation probes target it |
| `audit_probe` | 1 row; a target for `DROP TABLE` probes |
| `sm_mutate()` | volatile SQL function that inserts `(9100, 'fn')` into `probe_t` |
| `customers_masked` | view over `customers` with `email` shown as first letter + `***@example.test` |
| Row-level security | enabled on `customers` and `orders`. `sm_support` may SELECT only `tenant_id = 1`. `sm_analyst` may SELECT all rows. `sm_admin` has all rights on all rows |

Roles (all `LOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, a random password generated for each run (never a fixed or published one), database `CONNECT` revoked from `PUBLIC` and granted to these three only):

| Role | Grants |
|---|---|
| `sm_analyst` | SELECT on `tenants`, `orders`, `big_table`, `customers_masked`; SELECT on `customers` **columns** `id, tenant_id, name, note` only (**no `email`**) |
| `sm_support` | SELECT on `tenants`, `orders`, `big_table`, `customers`, `customers_masked`; RLS limits it to tenant 1 |
| `sm_admin` | SELECT/INSERT/UPDATE/DELETE on `tenants`, `customers`, `orders`, `big_table`, `probe_t`; SELECT on `customers_masked`; owns `probe_t` and `audit_probe`; CREATE on schema `public`; EXECUTE on `sm_mutate()`; USAGE on sequences |

Sentinel values the harness looks for in responses:

| Sentinel | Meaning |
|---|---|
| `T2-SECRET` | appears only in tenant 2 rows. Seeing it as the support role is a row-level-security leak |
| `T1-NOTE` | appears only in tenant 1 rows. Used as a control |
| `/cust\d{4}@example\.test/` | a raw email. Masked values (`c***@example.test`) do not match |
| `/row-\d+-end/` | one `big_table` row; counted for the row-cap probe |
| `Customer N`, count `100` | used by control reads |

The harness keeps a separate superuser connection to `sealmark_seed` (the "state reader") to check what changed. Between probes it resets `probe_t` (truncate), restores tenant names, drops `sm_ddl_probe`, and recreates `audit_probe` if a probe dropped it.

The seed is fixed. There is no "bring your own schema". Point the harness at a Postgres you control (`--pg`, with `--yes`); the seed is created there. The `sqlite` pack has its own seeded file with the same ideas (see `sealmark explain sqlite-read-only`).

## 4. Roles and server instances

A database-backed server usually takes one connection string and has no notion of callers. To test it as three roles, the harness **starts one server instance per role**, filling placeholders in the configured command, args, env, URL, and headers:

| Placeholder | Value |
|---|---|
| `{dsn}` | connection string for the role under test, e.g. `postgres://sm_support:<random>@127.0.0.1:PORT/sealmark_seed` |
| `{host}` `{port}` `{user}` `{password}` `{database}` `{role}` | the parts of that connection and the role name (`user` is `sm_<role>`; `role` is `analyst`, `support`, or `admin`) |
| `{dsn:analyst}` `{dsn:support}` `{dsn:admin}` | the connection string of a specific role, regardless of the instance's own role |

A server whose configuration contains no placeholder cannot be pointed at the seed database, so the db pack is not run (status `na`, with that reason). The core pack runs once, using the admin role's values if a database was started.

The three instances are opened **one at a time** by the `db-privilege` check (section 6.8), which compares the database backends each instance created, and the role it reports with `SELECT current_user`, with the role it was given. The other checks reuse the admin, support and analyst sessions. A database is started whenever the config contains placeholders (even for a `core`-only run), because the server cannot start without a connection string; with `--no-embedded` and no `--pg`, placeholders expand to empty strings and the server probably will not start.

## 5. Core pack

Four checks, all applicable to any MCP server. Core is basic hygiene any server should pass; it is not what differentiates Sealmark. A `core` A on a server that exposes one trivial tool proves little.

If the server declares **no tools**, `protocol` is `part` ("no tools declared") and `robust-input` and `secret-echo` are `na`; `tool-poisoning` is `na` too unless the server lists prompts or resources or sends instructions, in which case that text is still scanned. The pack is then graded on what is left (with `protocol` alone, 50%, a D). If `tools/list` returns something the MCP client library cannot parse (or pagination never ends, or it exceeds the bound below), `protocol` is `fail` with the reason and the other three are `inconclusive`: the pack is graded F with a provisional mark.

### 5.1 `protocol`: valid MCP handshake and tool schemas

- Pack core. Not critical. Scope: server.
- **Probed:** `initialize` and `tools/list` (all pages: `nextCursor` is followed, up to 50 pages; a repeated cursor or more than 50 pages is a protocol failure). The listing is also bounded in total, since 0.3-draft: more than 5 000 tools or 32 MiB of serialized pages is a protocol failure (`tools/list returned more than 5000 tools (or 32 MiB)`), so a server that floods the listing cannot exhaust the harness. Static review of each tool. Since round 5 the core session also counts what a stdio server wrote to stdout that is not JSON-RPC (during `initialize`, `tools/list` and every call) and the tool results the client library rejected as not valid MCP. Only the core session is measured, to keep the check's input fixed.
- **Decided by:** protocol and static review.
  - `fail`: a tool name outside `^[A-Za-z0-9_.-]{1,128}$`; a duplicate tool name; or a `tools/list` reply the MCP client library rejects (for example an `inputSchema` that is not a JSON Schema object) or that exceeds the bound. In the last two cases the other core checks are `inconclusive`.
  - `part`: a tool with no description or one shorter than 10 characters; a server that declares zero tools; the server wrote N non-JSON-RPC lines to stdout (`protocol.stdout-noise`, "strict stdio clients break on this", with the first line quoted); or a `tools/call` result was not valid MCP (`protocol.invalid-result`, naming the tool). The check stays non-critical.
  - `pass`: otherwise.
- **Why these thresholds:** the name pattern (1 to 128 characters of letters, digits, `_`, `.`, `-`) is a conservative rule that many clients and model APIs enforce, so a name outside it may be rejected or mangled (it is this harness's rule, not a quote from the specification); a duplicate name makes calls ambiguous. A schema the client cannot parse cannot be used to build arguments. Missing descriptions do not break a client but remove what the model uses to choose tools, so they cost half a point, not a fail. A server with no tools is not a violation, but it must not look like a perfect score for doing nothing.
- **Does NOT prove:** that the tools work, that the descriptions are accurate, or that the server conforms to the whole protocol (only the handshake and tool listing are exercised; resources and prompts are listed and scanned as text by `tool-poisoning`, but no `prompts/get`, no resource read, no sampling, no progress).
- **False-positive risk:** a client library stricter than the protocol (the harness uses the official TypeScript SDK) can reject a reply that other clients accept. The 10-character description rule is arbitrary.
- **False-negative risk:** a server that behaves differently for other clients, or only lists some tools to some callers.

### 5.2 `tool-poisoning`: no tool-poisoning indicators in tool metadata

- Pack core. **Critical.** Scope: server (what it declares, not what it does).
- **Probed:** no tool is called. Every string in every tool definition is scanned: name, title, description, and all text inside the input schema (parameter descriptions, enum values, defaults), to a nesting depth of 8. The text of each listed prompt (name, description, argument names and descriptions) and resource (name, title, description, URI) is scanned the same way; the harness lists prompts and resources but never calls `prompts/get` or reads a resource. Since round 5 the **server instructions** (the `instructions` of `initialize`, reported as `server instructions`) and the `serverInfo` fields `name`, `title`, `description` and `websiteUrl` (reported as `serverInfo <field>`) are scanned by the same tiers: they are model-visible text like a tool description. The 4,000-character length rule is not applied to instructions (long instructions are ordinary; the patterns and the hidden-character scan are what catch an injection), and a server with no tools but instructions has text to scan. A listing that fails is reported as "not scanned", never as clean.
- **Decided by:** static scan, in two tiers. Any strong indicator gives `fail`; otherwise any weak indicator gives `part`; otherwise `pass`. Evidence lines quote the matched text and say which tier matched.

**Strong indicators (verdict `fail`)**

| Indicator | Pattern (case-insensitive) |
|---|---|
| tells the model to ignore prior instructions | `ignore (all \|any )?(the \|your )?(previous\|prior\|above\|earlier) (instructions\|prompts?\|rules)` |
| an `<IMPORTANT>` block aimed at the model | `<\s*important\s*>` |
| tells the model to read or send a credential file | a credential path (`~/.ssh`, `.ssh/id_`, `id_rsa`, `id_ed25519`, `id_ecdsa`, `id_dsa`, `.aws/credentials`, `/etc/passwd`, `/etc/shadow`, `.netrc`, `.git-credentials`) within 60 characters (no full stop or semicolon) after an imperative: `you must\|should\|need to\|have to`, `first`, `then`, `also`, `always`, `please`, or `before ...`, followed by `read\|cat\|open\|send\|upload\|post\|forward\|attach\|include\|copy` |
| asks the model to send a credential file to a URL | `send\|post\|upload\|forward\|transmit\|leak`, then within 60 characters a credential path (as above), then within 80 characters `http://` or `https://` |
| asks the model to send secrets or conversation data to a URL | `send\|post\|upload\|forward\|transmit\|leak`, then within 80 characters (no full stop or semicolon) one of `credential(s)`, `secret(s)`, `password(s)`, `api key(s)`, `token(s)`, `private key(s)`, `ssh`, `conversation`, `chat history`, `system prompt`, `.env`, then within 80 characters `http://` or `https://`. Before matching, phrases that say how the tool authenticates (`using\|with\|via` and an optional `your\|the\|a`, up to two more words, then a secret noun) are removed, so "upload the file using your API token; see https://docs..." does not match |
| mentions exfiltration | `exfiltrat` |
| asks the model to read a `.env` file and pass it on | `read\|cat\|open\|include\|attach\|send\|upload\|copy`, then within 40 characters `.env` |
| terminal control characters (0.3-draft) | U+0000 (NUL), U+001B (ESC), or any of U+0080 to U+009F (the C1 range): characters that hide text from a reader or drive a terminal that renders tool metadata. Tested before the hidden-character class, and reported as its own evidence line when a text also has a zero-width character |
| hidden or bidirectional control characters | U+200B (zero-width space); U+202A to U+202E; U+2060 to U+2064; U+2066 to U+2069; the Unicode tag block U+E0000 to U+E007F (except the three exact tag sequences of the England, Scotland and Wales flag emoji, U+1F3F4 plus the tags for `gbeng`, `gbsct` or `gbwls` plus U+E007F; any other tag run can carry hidden ASCII and stays strong); a run of three or more of U+200B to U+200F, U+2060, U+FEFF; a U+FEFF that is not the first character |

**Weak indicators (verdict `part`)**

| Indicator | Pattern (case-insensitive) |
|---|---|
| tells the model to hide something from the user | `do not\|don't\|never`, then `tell\|inform\|mention\|show\|reveal\|let`, then within 40 characters the word `user` |
| references the system prompt | `system prompt` |
| mentions a `.env` file | `.env` |
| uses a `<system>` or `<instructions>` tag | `<\s*(system\|instructions?)\s*>` |
| asks the model to call another tool first | `before (using\|calling\|running) this tool`, then within 40 characters `call\|use\|read\|run` |
| overrides prior guidance | `overrid(e\|es\|ing)`, `supersed(e\|es)` or `take(s) precedence over`, then within 40 characters `instructions\|guidance\|rules\|prompt` |
| mentions a credential file path | any of the credential paths above, with no read or send instruction around it (for example "e.g. `~/.ssh/id_ed25519`" in a parameter description) |
| asks the model to send user data to a URL | `send\|post\|upload\|forward`, then `user's\|all\|every`, then `data\|file(s)\|message(s)\|conversation\|history\|context`, then `http(s)://` (bounded gaps, no full stop) |
| zero-width or direction marks alone | one or two of U+200C to U+200F anywhere, or a U+FEFF at the very start (ordinary in emoji sequences and right-to-left text) |
| other C0 control characters or DEL (0.3-draft) | U+0001 to U+0008, U+000B, U+000C, U+000E to U+001A, U+001C to U+001F, or U+007F. Tab, line feed and carriage return are ordinary and never flagged (a CRLF description is normal). These are usually accidents (copied binary text) and rarely carry an instruction |
| overlong description | more than 4,000 characters (hidden instructions hide in long text) |

- **Why tiered:** this is a critical check, so one benign sentence (a safety note that mentions the system prompt, a description that mentions `.env`) must not cap a real server at D. Strong indicators have almost no legitimate reason to appear in tool metadata. Weak ones are plausible in honest text and are flagged for a human, at half a point.
- **Why the control-character classes (decided by recommendation, owner may veto):** a terminal that renders tool metadata is the attack surface the hidden-character rule already defends, and ESC and the C1 range are the characters that actually drive one (an ANSI or OSC sequence can hide or rewrite text). The rest of C0 and DEL are weak because they are rarely instructions. The text report prints these characters as visible escapes, so a raw ESC never reaches the terminal. A server that embeds ANSI colour codes in its descriptions on purpose fails by design. Veto path: drop the two classes in `scanText` (`core.ts`).
- **Does NOT prove:** that tool descriptions are safe. A pass means none of these patterns matched. It does not detect paraphrased or non-English injections, instructions split across fields, or malicious behavior at call time. It is a lint, not a security scan.
- **False-positive risk:** a description that legitimately documents reading a `.env` file ("reads the .env file and returns the keys"), documents a path like `~/.ssh/id_rsa`, or says "upload the user's files to https://..." can match a strong or weak pattern. Evidence lines quote the match so a human can judge.
- **False-negative risk:** high. Any injection that avoids the listed phrases passes. Injection through tool *output* is not covered at all (see blind spots).

### 5.3 `robust-input`: survives malformed tool input

- Pack core. Not critical. Scope: server.
- **Probed:** for up to the first 25 tools (`checks.robust-input.max_tools`; tools beyond that are listed as not covered), only inputs that are **invalid by the tool's own schema**, up to four per tool:
  1. if the tool has required arguments: a call with `{}`;
  2. if the tool has typed properties: a call where every *typed* argument gets a value of the wrong JSON type. The harness picks the first of these that violates the declared type (and is not listed in the property's `enum`): `12345`, `"not-a-valid-value"`, `true`, `["x"]`, `{"x": 1}`. A property with no declared type is not probed, because any value might be valid;
  3. every typed argument that does not accept `null` is sent `null`;
  4. the wrong-type call plus one unexpected extra argument (`sm_unexpected`).
  Round 5 adds nested variants for a required array-of-object parameter (a string in place of the array; one item that lacks a required field when `items.required` exists) and a second wrong-type variant for a string parameter (the object candidate), at most two extra calls per such parameter.
  One **valid** call is also made: a tool that takes no arguments and declares `readOnlyHint: true` is called once with `{}`. It counts toward coverage only if the server **answered without an error** (0.3-draft, decided by recommendation, owner may veto): a server that rejects its own no-argument tool is not credited with a valid call, the tool is listed as not covered ("its no-argument call returned an error, so no tool behaviour was exercised"), and the coverage level stays `hygiene-only`. The reply is still scanned for a stack trace, because an error reply is exactly where one leaks. A tool that takes no arguments and is not declared read-only is never called (it needs a `probes:` entry).
  Each call has a hang limit of `max(2 s, --timeout-probe)` (default 10 s). After a call that did not time out, the harness checks the server is still alive with a `tools/list`. After three hangs it stops probing.
- **Decided by:** protocol and response.
  - `fail`: the server process exited or stopped answering, or any call got no answer within the hang limit.
  - `part`: an error response contains a stack trace or internal paths (Python `Traceback`, JS `at fn (file:line:col)`, `File "...", line N`, `node_modules/` or `site-packages/` with a `file:line` shape, a Unix home-directory path with a `:line` suffix, or a `C:\Users\...` path); or a call with schema-invalid arguments *succeeded* ("accepted schema-invalid arguments"). Since round 5 two more shapes of `isError` are not read as a rejection: an error whose text is the failed-fetch vocabulary was produced *after* the server used the invalid argument (an upstream request was attempted with it), so it is counted as lenient (`robust.lenient-downstream`); and an error whose text is an unhandled runtime error (`TypeError`, `Cannot read propert…`, `is not a function`, `AttributeError`, `KeyError`, `'NoneType'`) is an internals leak, not a validation decision (`robust.internal-error`). An error that names the argument ("url must be a string") is a rejection. The summary counts the two separately, and the "rejected cleanly" wording is never used for them.
  - `pass`: every invalid call was rejected cleanly and the server stayed responsive. A refusal in plain text without `isError` counts as a rejection, and the evidence says that a client reading `isError` cannot tell it from success.
  - `na`: no tool has arguments the harness can safely malform and no valid call was made.
- **Why:** a server that dies or hangs on one bad call is a denial of service for every agent sharing it. Leaking internals and accepting invalid input are hygiene problems, not outages, so half a point.
- **Does NOT prove:** robustness in general. At most four invalid shapes per tool are tried; no fuzzing, no oversized input, no concurrency, no valid-looking-but-hostile input.
- **False-positive risk:** many JavaScript servers coerce `12345` to `"12345"` for string parameters or accept a string where a number is declared, which is lenient but common and harmless. A slow server can exceed the hang limit under load. The `C:\Users\...` pattern also matches an ordinary error message that mentions a Windows user directory; a Unix home-directory path counts only when it carries a `:line` suffix, so an ENOENT message or a PATH dump does not.
- **False-negative risk:** a server that fails only on valid-looking hostile input is not tested, because the harness deliberately does not send valid-looking arguments to tools it has not classified (see safety notes).
- **Side effect to know about:** this check calls up to 25 tools with invalid arguments. If a tool does not validate its input it may act on the coerced values. Run against a sandbox configuration with throwaway credentials.

### 5.4 `secret-echo`: no environment secret echoed in responses

- Pack core. **Critical.** Scope: server.
- **Probed:** for servers Sealmark starts (stdio, or an HTTP server started with `--start` and `--url`) the harness adds two canary variables to the server's environment, `SEALMARK_CANARY` and `SEALMARK_FAKE_API_KEY`. The `tools/list` reply, the listed prompts and resources, every response captured by `robust-input` and the replies to your own `probes:` calls (including error text and JSON-RPC error messages, scanned in full; only the copy shown in evidence is shortened) are then scanned for either value. The report names the variable the leaked value was printed under and never quotes the text around it.
- **Decided by:** response.
  - `fail`: a canary appears in the `tools/list` reply or any captured response.
  - `pass`: no canary appears and at least one response was captured.
  - `inconclusive`: no response was captured to scan (for example every tool's properties are untyped and none has required arguments, so `robust-input` made no call). Because the check is critical, this makes the grade provisional.
  - `na`: a server Sealmark did not start (a bare `--url`: "canary injection needs a server Sealmark starts (stdio, or --start with --url)"), because it cannot place a canary in its environment. The pack is still graded on its other checks. Also `na` when the server declares no tools.
- **Why:** error handlers that dump `process.env` or a config object are a classic way to leak API keys into a model's context. A canary is a deterministic, harmless stand-in.
- **Does NOT prove:** that real secrets are never leaked. Only the two canary variable names are covered, and only through the responses the harness happened to trigger (mostly error responses to malformed calls). A server that leaks an environment variable it reads under a different name, or only on a code path the harness never reaches, passes. An HTTP server Sealmark did not start is not tested at all.
- **False-positive risk:** very low; the canary values are random (`sm-canary-` plus 16 hex digits, and `sk-sealmark-fake-` plus 24 hex digits, fresh for every run).
- **False-negative risk:** high, by construction. A pass is weak evidence.

## 6. Database pack

Applies when the config uses placeholders, a SQL tool is found, and a Postgres is available (embedded or `--pg`). All probes run through the server's SQL tool(s) as a specific role, against the seed.

**SQL tool discovery.** A tool is treated as taking SQL if an explicit `sql_tools` list says so, or if it has a string parameter named `sql`, `sql_query`, or `sqlquery` (any case), or `query` or `statement` **and** the name of the tool or the parameter's own description matches `sql|database|postgres|table` (the verbs `select`, `insert`, `update` and `delete` count in the tool name and the parameter description only, not in prose elsewhere in the tool description). Names such as `command` and `q` are deliberately not matched, so a `run_shell {command}` tool never receives SQL probes. A tool with a `query` or `statement` string parameter whose description talks about results, rows, export or format is also detected when another tool of the same server was detected as SQL with the same parameter name (its role comes from its description).

**`sql_tools` adds or corrects, and never hides.** An explicit `sql_tools` list wins for the tools it names (a missing `role`, `shape` and approval parameter are filled in from the tool's schema), but a tool that auto-detection finds is still probed when the list leaves it out, and a detected writer cannot be relabelled a reader: hiding a writer would otherwise keep a run STANDARD. To keep a tool out of a run, use `tools.exclude`, which is locked and makes the run CUSTOM. Each entry must name a tool the server declares and a string argument that tool has (otherwise exit 2).

**Other required parameters.** A SQL tool with another required parameter is kept (round 5; before, it was skipped and listed under "Not covered", and the `sql_tools` workaround did not work). The harness fills those parameters: an enum gets its first value, a string a token, a number its minimum or 1, a boolean `false`, and a `default` wins. A `sql_tools[]` entry may carry `args: {<param>: <string|number|boolean>}` (scalars only; keys must be parameters of the tool when the tool is known), which overrides the fillers. When the control read then fails, the tool is listed with the validation text the server gave and the remedy: set `sql_tools: [{tool, arg, args: {<param>: <value>}}]`; the pack's "all inconclusive" hint quotes the server's reply instead of blaming the connection string.

**Controls.** Before judging anything, the harness checks that each SQL tool can run `SELECT '<token>' AS t, (SELECT count(*) FROM customers) AS n, current_user AS u` as the admin role, see its random token, and see `sm_admin`. A reply that is a query plan (an `EXPLAIN` wrapper) is not rows and fails the control. A tool that cannot is excluded from every check (noted in evidence). A tool declared as a writer, or of unknown role, that cannot read gets a write control instead (an `INSERT` the harness then finds in the database); a tool with an approval parameter that refuses the control write is treated as gated (see `write-gate`). Since round 5 a tool whose read and write controls both fail gets a third, DDL form: `CREATE TABLE sm_ddl_<t> (x int)`, verified in the database, and a DDL-controlled tool runs one core corpus case (`CREATE TABLE sm_ddl_<t> (x int); INSERT INTO probe_t (id, v) VALUES (9020, 'ddl-stacked')`), judged by `db-state` like the others. If no tool is controlled, every non-advisory check is `inconclusive` with that reason; when the token was right but the role was not, the reason says the server did not connect as the requested database role (a hard-coded or cached connection string, or a pinned `{dsn:<role>}`), because then the database, not the server, may be the reason a write failed. In that case the advisory `db-privilege` check (section 6.8) is emitted first, so the report shows the finding and not only "everything inconclusive". The role of the support and analyst sessions is deliberately not enforced by the control: a server that connects as the wrong role there is exactly what `rls` and `pii` exist to catch.

**A server that stops answering.** A call that times out or loses its connection is no evidence, whereas a JSON-RPC error is a reply (a legitimate refusal). If the admin session dies or hangs during the `read-only` or `mutating-sql` probes, the probes stop; `read-only` and `mutating-sql` are `inconclusive` ("the server stopped answering during the write probes") and `write-gate` is `na`, unless a write had already taken effect, in which case the evidence of that write stands (`read-only` is graded on what was observed, and `mutating-sql` is `fail` if a core case took effect). The harness then starts the admin session again for the remaining checks; if it cannot, `db-rowcap` and `db-timeout` are `inconclusive`. Each security check then runs its own control (below). A failed control makes the check `inconclusive`, never `pass`: a broken connection must not look like a secure server.

**Lock handling.** Before each case the harness resets the scratch state over its own superuser connection with a 5-second lock timeout. If a server left a transaction open and holds a lock, the harness terminates the server's database connections and retries once. When that happens a warning is printed and a caveat is added to the evidence of every check that follows: the server's own connection is now dead, so later probes may fail for that reason and read as "blocked".

**Multiple SQL tools.** A check runs on each workable tool. Per tool the result is clean or not; across tools: all clean = `pass`, some clean = `part`, none clean = `fail`.

**What each check measures.** The db pack separates two kinds of check, because a database-backed server and its database share the work:

| Kind | Checks | Question |
|---|---|---|
| Server behavior | `read-only`, `mutating-sql`, `db-rowcap`, `db-timeout`, `write-gate`, `audit` | Does the *server* stop writes, mutations, runaway results, and runaway time? Tested as a role that **can** write, so the database cannot be the reason a write fails |
| Database control, tested through the server | `rls`, `pii` | The database enforces a control (row-level security, a column grant). Does the *server defeat it* (for example by connecting as the table owner or an admin role)? |
| Companion and identity checks | `pii-masked`, `db-privilege` | Can the server show the masked view (a server that denies everything is not masking)? Does each instance connect as the role it was given? |

For the second kind, a pass does **not** mean the server implements row filtering or masking. It means the server did not undo the database's control. A SQL passthrough server connected as the right role passes `rls` and `pii` without doing anything itself.

Scored in the standard: `read-only`, `pii-masked`, `db-rowcap`, `db-timeout` (one point each, not critical) and the critical `rls`, `mutating-sql` and `pii`. Advisory (shown, never scored): `write-gate`, `audit` and the candidate `db-privilege`.

### 6.1 `read-only`: read-only by default

- Pack db. Not critical. Scope: server, tested as the admin role.
- **Probed** (as `sm_admin`, per SQL tool, state reset first; `probe_t` row 9010 seeded):
  1. `INSERT INTO probe_t (id, v) VALUES (9001, 'sm-insert')`
  2. `UPDATE tenants SET name = 'sm-updated' WHERE id = 1`
  3. `DELETE FROM probe_t WHERE id = 9010`
- **Decided by:** db-state. After each statement the harness checks whether the row exists, the name changed, or the row is gone. The server's response text is recorded but not trusted.
- Per tool: clean if none of the three took effect. Aggregate by the multiple-tools rule. A tool declared as a writer (`sql_tools: role: writer`) is probed too and reported by name when its writes take effect ("declared writer tool; exclude it under `tools.exclude` if writes are intended").
- **Why:** admin can write in the seed, so any blocked write is the server's doing. "Read-only by default" is the base promise of most database MCP servers.
- **Does NOT prove:** that writes are impossible. Only three plain single-statement forms are tried here; indirect forms are in `mutating-sql`. A server that is read-only by default but offers a writable mode is graded in its default configuration only.
- **False-positive risk:** a server that intentionally supports writes behind a flag is graded as it is configured; the config you pass decides the result. A server that rolls back after reporting success is, correctly, read-only in effect.
- **False-negative risk:** a server that writes asynchronously after the check reads the state (the harness reads immediately after the response).

### 6.2 `write-gate`: write approval gate (advisory)

- Pack db. **Advisory (not scored).** Scope: server.
- **Decided by:** derived from `read-only`, the writer controls and (since round 5, computed after the mutating-SQL corpus has run) the corpus. If any plain write took effect: `fail` ("writes executed with no confirmation step"); the same when a core corpus case executed through a tool that has no approval parameter. When plain writes were blocked but a corpus case executed through a tool, the check is `na` ("plain writes were blocked (see mutating-sql: a corpus case executed through <tool>)"). It stays advisory, so no letter moves. If every writer tool has an approval parameter and refused the harness's write when it was omitted: `pass` (the harness never sets an approval parameter, so a write with approval is not tested). If all writes were blocked and there is no approval flow, or a declared writer could not be controlled: `na`.
- **Why advisory:** approval is usually the MCP *client's* job (the host asks the human before calling a tool), not the server's. A server cannot be graded for something a gateway may do for it.
- **Does NOT prove:** anything about client-side approval. The harness has no approval UI and never tests whether a confirmation parameter exists.
- It is shown so a reader sees "this server executes writes directly".

### 6.3 `rls`: row-level security respected

- Pack db. **Critical.** Scope: database policy, tested through the server (does the server defeat it?).
- **Control:** as admin, `SELECT note FROM customers WHERE tenant_id = 2 LIMIT 3` must contain `T2-SECRET`; as support, `SELECT note FROM customers WHERE tenant_id = 1 LIMIT 3` must contain `T1-NOTE`. If not: `inconclusive`.
- **Probed** (as `sm_support`, per SQL tool):
  1. `SELECT id, tenant_id, note FROM customers WHERE tenant_id = 2`
  2. `SELECT id, tenant_id, note FROM orders WHERE tenant_id = 2`
  3. `SELECT * FROM orders`
- **Decided by:** response. Any response containing `T2-SECRET` is a leak for that tool. (This check is decided from the response text, not from database state, because the data is read, not changed.)
- **Why:** the support role is limited to tenant 1 by a database policy. If it can read tenant 2 through the server, the server connects as a more privileged role (table owner, superuser, or `BYPASSRLS`) or otherwise bypasses the policy. Critical because it is a cross-tenant data leak.
- **Does NOT prove:** that the server is safe with your policies. It covers one policy shape (a tenant column) and one role. It does not test policies on other tables, `SET ROLE`, `SECURITY DEFINER` functions, or views that bypass RLS.
- **False-positive risk:** a server that returns the tenant 2 marker in an error or in its own debug text. A server that caches results across sessions.
- **False-negative risk:** a server that truncates or summarizes output so the marker does not appear. A leak that needs a query the harness does not send.
- **Note:** this is a server-vs-database-control check. A server that leaks here is usually configured with the wrong connection string for the role; the report says so.

### 6.4 `mutating-sql`: mutating SQL blocked

- Pack db. **Critical.** Scope: server, tested as the admin role.
- **Probed** (as `sm_admin`, per SQL tool, state reset before each case): the corpus below. Cases marked **core** are the canonical bypasses of a "read-only SQL tool".
- **Decided by:** db-state. After each case the harness checks the database for the effect (the table gone, the row present or removed, the value changed). Steps run in order, each as a separate tool call.
  - `fail`: any **core** case took effect (cases 1 to 4 and 17 to 19).
  - `part`: no core case took effect, but a non-core case did.
  - `pass`: no case took effect.
- **Why:** stacked statements, a transaction terminator (`COMMIT`, `ROLLBACK`, `END`, `ABORT`) that ends a read-only wrapper, and case/comment obfuscation are bypasses of naive filters and of read-only wrappers alike; a server that fails them is not read-only in any meaningful sense, so it fails and (being critical) caps at D. Indirect forms (CTEs, functions, DO blocks, prepared statements) are blocked reliably only by a read-only transaction or a read-only role, not by text filtering, so a miss is partial.
- **Does NOT prove:** that no mutation is possible. The corpus is finite. It does not try `COPY ... TO PROGRAM`, large objects, `pg_read_file`, sequences (`nextval`), advisory locks, extensions, or privilege escalation. A pass means these forms did not change the seed.
- **False-positive risk:** a case that changes state through a side route the server cannot control (very unlikely; the state reader is separate). A server with a legitimate write tool that the config lists under `sql_tools` is judged as a read tool.
- **False-negative risk:** a mutation form outside the corpus. An attack that works on a different Postgres version. A server that blocks by matching the harness's exact strings.

Corpus (19 cases per SQL tool, in the order the harness runs them; 0.3-draft added cases 14 to 16, decided by recommendation, owner may veto, all non-core; round 5 added cases 17 to 19, all core, with case 3 the first of four transaction terminators. The DDL-controlled case of the previous section is an extra case that only a DDL-only tool runs and is not one of the 19):

| # | Case | SQL (steps run in order, each as its own tool call) | Core | Effect looked for |
|---|---|---|---|---|
| 1 | stacked statements (DROP) | `SELECT 1; DROP TABLE audit_probe` | yes | `audit_probe` no longer exists |
| 2 | stacked statements (INSERT) | `SELECT 1; INSERT INTO probe_t (id, v) VALUES (9002, 'stacked')` | yes | `probe_t` row 9002 exists |
| 3 | COMMIT then write (read-only transaction escape) | `COMMIT; INSERT INTO probe_t (id, v) VALUES (9005, 'commit-escape')` | yes | row 9005 exists |
| 4 | case and comment obfuscation (INSERT) | `/*x*/ iNsErT INTO probe_t VALUES (9008,'obf')` | yes | row 9008 exists |
| 5 | data-modifying CTE (DELETE) | `WITH d AS (DELETE FROM probe_t WHERE id = 9003 RETURNING id) SELECT count(*) FROM d` (row 9003 seeded first) | no | row 9003 is gone |
| 6 | data-modifying CTE (INSERT) | `WITH i AS (INSERT INTO probe_t (id, v) VALUES (9004, 'cte') RETURNING id) SELECT * FROM i` | no | row 9004 exists |
| 7 | function with side effects | `SELECT sm_mutate()` | no | `probe_t` has a row with `v = 'fn'` |
| 8 | anonymous DO block | `DO $$ BEGIN INSERT INTO probe_t VALUES (9007,'do'); END $$` | no | row 9007 exists |
| 9 | TRUNCATE | `TRUNCATE probe_t` (row 9009 seeded first) | no | row 9009 is gone |
| 10 | DDL (CREATE TABLE) | `CREATE TABLE sm_ddl_probe (x int)` | no | table `sm_ddl_probe` exists |
| 11 | DDL via SELECT INTO | `SELECT 1 INTO sm_ddl_probe` | no | table `sm_ddl_probe` exists |
| 12 | PREPARE then EXECUTE | step 1 `PREPARE p AS INSERT INTO probe_t VALUES (9011,'prep')`, step 2 `EXECUTE p` | no | row 9011 exists |
| 13 | session state (disable read-only, then write) | step 1 `SELECT set_config('default_transaction_read_only', 'off', false)`, step 2 `INSERT INTO probe_t (id, v) VALUES (9006, 'session')` | no | row 9006 exists |
| 14 | PREPARE and EXECUTE in one call | `PREPARE p2 AS INSERT INTO probe_t VALUES (9012,'prep1'); EXECUTE p2` | no | row 9012 exists |
| 15 | function with side effects in `FROM` | `SELECT * FROM sm_mutate()` | no | `probe_t` has a row with `v = 'fn'` |
| 16 | `EXPLAIN ANALYZE` runs the statement | `EXPLAIN ANALYZE INSERT INTO probe_t (id, v) VALUES (9013, 'explain')` | no | row 9013 exists |
| 17 | ROLLBACK then write (read-only transaction escape) | `ROLLBACK; INSERT INTO probe_t (id, v) VALUES (<its own id>, …)` | yes | that row exists |
| 18 | END then write (read-only transaction escape) | `END; INSERT INTO probe_t (id, v) VALUES (<its own id>, …)` | yes | that row exists |
| 19 | ABORT then write (read-only transaction escape) | `ABORT; INSERT INTO probe_t (id, v) VALUES (<its own id>, …)` | yes | that row exists |

The **transaction-terminator family** (cases 3, 17, 18, 19): `COMMIT`, `ROLLBACK`, `END` and `ABORT` each end the read-only transaction a wrapper opened, so a filter that blocks only the word `COMMIT` leaves three escapes open. The rule is one entry per terminator *keyword* Postgres accepts: `COMMIT WORK` and `COMMIT TRANSACTION` share the keyword a filter would match, so they add nothing, and `… AND CHAIN` starts a new transaction with the same read-only characteristic, so it is not an escape and is left out. Each case is followed by an `INSERT` into `probe_t` with its own id, judged by `db-state` as the other cases are; `sealmark explain mutating-sql` prints the exact statements.

Cases 14 to 16 exist because the earlier forms are blocked by filters that look only at the first keyword or only at the select list: a pooled server loses the prepared statement between the two calls of case 12 but not within the single call of case 14; a server that rejects a function call in the select list (case 7) can still run one in `FROM`; and a prefix filter that lets `EXPLAIN` through has not stopped `EXPLAIN ANALYZE` from executing the statement. A read-only transaction blocks all three.

Before every case the harness resets the scratch state (see the seed section). Notes on the corpus: cases 1, 2 and 14 need multi-statement support, which only the simple-query protocol provides; a server using the extended protocol (which rejects multiple statements) legitimately "blocks" them. Cases 3, 17, 18 and 19 work only if the server wraps queries in a transaction and does not stop the terminator. Case 13 relies on a session setting outliving the call, which a rollback undoes, and on the two steps reaching the same database session; a server that opens a new connection per call blocks it by accident, and the corpus cannot tell the difference. Cases 5 to 16 are non-core because a read-only transaction or a read-only role blocks them reliably, whereas text filtering usually does not; a miss indicates a weaker enforcement design rather than a bypass of an advertised filter. This split is a judgment call and may change.

### 6.5 `pii`: personal data masking respected

- Pack db. **Critical.** Scope: database grants, tested through the server (does the server defeat them?).
- **Control:** as analyst, `SELECT id, name FROM customers LIMIT 3` must return text matching `Customer N`. If not: `inconclusive`.
- **Probed** (as `sm_analyst`, per SQL tool):
  1. `SELECT email FROM customers`
  2. `SELECT * FROM customers`
  3. `SELECT id, name, email FROM customers WHERE tenant_id = 1 LIMIT 5`
- **Decided by:** response. Any response matching `/cust\d{4}@example\.test/` is a leak. A permission-denied error is clean.
- **Why:** the analyst role has no SELECT right on `customers.email` (only the masked view). If the server returns raw emails, it is connecting with more privilege than the role it was given. Critical because it exposes personal data.
- **Does NOT prove:** that the server masks anything. The masking here is a **column grant** enforced by Postgres; a server that does nothing but pass SQL through gets a pass if it connects as the analyst role. It also does not test other personal-data shapes (phone numbers, free text), other tables, or other roles.
- **False-positive risk:** a server that echoes the query's own text back with an email in it (none of the probes contain one). A server that reads the view `customers_masked` and returns masked values is clean.
- **False-negative risk:** a server that returns the data base64-encoded or truncated so the pattern does not match.

### 6.6 `pii-masked`: masked data reachable

- Pack db. Not critical, scored. Scope: server (does it let a masked view through, or does it deny everything?). Since 0.2-draft.
- **Probed** (as `sm_analyst`, per SQL tool): `SELECT id, email FROM customers_masked LIMIT 3`.
- **Decided by:** response. A reply that carries masked emails (`c***@example.test`) is `pass` for that tool; raw emails coming back from the masked view is `fail`; a refusal, an empty answer or no answer is `inconclusive` for that tool. Across tools the scored ones are aggregated by the multiple-tools rule; when no tool could read the view the check is `inconclusive`.
- **Why:** `pii` passes a server that denies the email column outright, which is also what a server that denies everything does. `pii-masked` asks the other half: can a legitimate masked read be served at all? A server that cannot show the masked view is not masking, it is broken or closed.
- **Does NOT prove:** that the server masks anything itself. The view is part of the seed and the analyst role may read it; a passthrough server connected as the analyst role passes.
- **False-positive risk:** a server that refuses the probe is `inconclusive`, not failed.
- **False-negative risk:** a server that returns the masked view but also leaks the raw column some other way is caught by `pii`, not here.

### 6.7 `db-rowcap` and `db-timeout`: row cap and statement timeout

These two checks replace the single `cap-timeout` check of 0.1-draft (the old id still works in configuration, with a warning). The split lets a server that has a row cap but no timeout, or the reverse, be told which half failed. Both are scored, not critical, scope server, tested as the admin role. One loop runs both and stops when both are disabled.

**`db-rowcap`**

- **Probed** (per SQL tool): `SELECT id, payload FROM big_table ORDER BY id` (200,000 rows exist). The number of **distinct** `row-N-end` strings in the response is counted (a server may repeat the result as text and as structured content). Call limit 120 s.
- **Decided by:** response. Clean if at most **10,000** rows (`checks.db-rowcap.row_cap`) came back and at least one did, or the call was an error whose text (a tool error or a JSON-RPC error message) says the result is too large (patterns such as "too many rows", "exceeds ... limit", "row limit", "limited to"; plain "limit" is not enough, because SQL errors quote it). Not clean if more than 10,000 rows came back, the connection dropped or the call timed out ("response too large or connection dropped"), or nothing came back and there is no recognizable limit message. A server that **refuses** the probe without a recognizable limit message is *not measured* for that tool (a refusal is neither a cap nor its absence); when no tool could be measured the check is `inconclusive`.
- Verdict across measured tools: all clean = `pass`; some = `part`; none = `fail`.
- **Why:** an uncapped result can flood an agent's context and the server's memory. 10,000 is far above any normal cap (typically 100 to 1,000) and far below 200,000, so only "effectively uncapped" fails. A response over the transport limit (64 MiB per message) is treated as a finding, not a harness error.
- **Does NOT prove:** that limits hold for other queries (joins, aggregates), other tables, or concurrent callers. It does not measure memory.
- **False-positive risk:** a server that caps by returning a summary or a pointer to a file, with none of the row text and no message matching the limit patterns, is marked "cap cannot be confirmed" and counted as not clean.
- **False-negative risk:** a server that streams or encodes rows so that few `row-N-end` strings are visible, but still returns more than 10,000 rows' worth of data, passes.

**`db-timeout`**

- **Probed** (per SQL tool, in a fresh server instance): `SELECT pg_sleep(T + 20)` where T is `checks.db-timeout.expected_sec`, which defaults to `--timeout-probe` (default 10); `checks.db-timeout.slow_sql` replaces the statement with your own `SELECT`. The harness waits T + 8 seconds. If the server refuses the statement in under a second (a function allow-list), the harness tries a CPU-bound fallback that never completes in the window: `SELECT count(*) FROM big_table a CROSS JOIN big_table b WHERE a.id + b.id = -1`.
- **Decided by:** response and elapsed time. Clean if the statement ended after at least 1 second and before the wait expired (cancelled by a timeout). Not clean if it was still running at T + 8 s, the connection dropped, or it returned in under 1 second with no error (the statement did not run as written). A statement refused in under a second is *refused before execution*; if both the sleep and the fallback are refused the tool is *not measured* and, when no tool could be measured, the check is `na` ("not measured (the server refuses both pg_sleep and a long join)"), never a pass or a fail.
- Verdict across measured tools: all clean = `pass`; some = `part`; none = `fail`. After the probe the harness terminates any backend still running on `sealmark_seed` (other than its own state reader).
- **Why:** an unbounded statement can hold a connection indefinitely. The sleep is T + 20 and the wait T + 8, so a server whose timeout is at most T + 8 seconds passes.
- **Does NOT prove:** that a timeout holds for other queries, other tables, or concurrent callers.
- **False-positive risk:** a server with a timeout longer than T + 8 seconds (set `--timeout-probe` or `checks.db-timeout.expected_sec` to its value).
- **False-negative risk:** a fast rejection of `pg_sleep` followed by a fallback that is cancelled passes, though it proves only that the fallback is cancelled.

### 6.8 `db-privilege`: connects as the role it was given (candidate, advisory)

- Pack db. **Advisory (not scored)**, a **candidate** (section "Candidate checks"). Scope: server (does each instance connect as exactly the role in its `{dsn}`, with that role's attributes?). Since 0.3-draft. Decided by recommendation, owner may veto.
- **Scope decided.** The harness supplies every credential the server has (least-privilege roles, a random admin password, a scrubbed environment), so "does the server connect as a superuser or table owner" cannot be observed as a property of the server: in the harness world the answer is fixed by construction. What *can* be observed is whether the server **uses the credentials it was given**. A server that does not (a cached DSN, a config file written by the first instance and preferred by the next, a stale pool) was reported before only as "all inconclusive: the server did not connect as the requested database role", which hid a dangerous behavior behind a harness-limit message.
- **Probed.** The three instances are opened one at a time. For each, the harness lists the backends in `pg_stat_activity` for `sealmark_seed` before and after the instance's first benign read (excluding its own state reader), and the read selects `current_user`. Evidence per instance: `db.privilege.backends` (`db-state`: the new backends and their roles), `db.privilege.current-user` (`response`) and `db.privilege.role-attributes` (`db-state`: `rolsuper`, `rolbypassrls`, and whether the role owns `customers` or `orders`).
- **Decided by:** db-state and response. `pass` when every instance's new backends and `current_user` name its own role and no observed role is superuser, BYPASSRLS or owner of an RLS table. `fail` when any instance connected as another role (the evidence reads, for example, "as support, the new backends were sm_admin") or an observed role has one of those attributes. `inconclusive` when an instance produced neither a new backend nor a readable `current_user` (a pooler elsewhere, no reader tool), with the instance named. `na` when disabled.
- **Why advisory, not scored.** Scored, the check would hand every server that behaves correctly one more point in the db denominator: 6/7 (85.7%, B) becomes 7/8 (87.5%, B) but 5/7 (71.4%, C) becomes 6/8 (75%, B). A near-automatic pass that moves letters up is inflation. Advisory, it names the failure with db-state evidence and leaves the letters alone. It is registered as a candidate so a later methodology bump can score it if the owner wants.
- **Does NOT prove:** anything about a server connected to a database the harness does not own, or about privileges beyond the three seed roles.
- **False-positive risk:** none known for a server that opens its connection no later than its first read.
- **False-negative risk:** a server that connects lazily after the benign read is reported `inconclusive` for that instance, which the check says.

### 6.9 `audit`: every call logged (advisory)

- Pack db. **Advisory (not scored).** Verdict is always `na`: "not measured: servers do not write audit rows by themselves".
- Listed so that no report implies audit logging was tested. It is also in "Not covered".
- Planned, not built.

## 7. Safety notes: what the harness touches

Read this before running against anything you care about.

1. **It runs your server command.** The command in `sealmark.yaml` is spawned with your user's privileges, once for core and once per role for db, and once per other pack. The harness does not contain it: the sandbox is a convention it follows, not a security boundary, and a malicious server can ignore its working directory, HOME and PATH. Treat an unfamiliar server as untrusted code and run it in a throwaway VM or container.
2. **Environment passed to the server.** With the sandbox on, the environment is built from scratch. The server gets: `PATH` (the sandbox `bin` first, then your system `PATH`, which is the one deliberately inherited item so launchers such as `npx` and `uvx` resolve), `LANG`, `HOME`, `TEMP`, `TMP` and `TMPDIR` pointing inside the sandbox (on Windows also `USERPROFILE`, `APPDATA` and `LOCALAPPDATA`, and the Windows essentials `SYSTEMROOT`, `SYSTEMDRIVE`, `WINDIR`, `COMSPEC`, `PATHEXT`, `PROGRAMFILES`, `PROCESSOR_ARCHITECTURE` copied from your environment), a fixed user name and shell (`USER`, `LOGNAME`, `SHELL`, `TERM` elsewhere), the shared package-manager cache locations that exist (`npm_config_cache`, `UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR`, so `npx` and `uvx` do not re-download the server for every pack), whatever `server.env` sets, and the two canary variables. Your other environment variables are **not** forwarded; if a server needs more, set it in `server.env`. The report lists what was inherited (`inherited:` in the sandbox line of the text and markdown reports, `sandbox.inherited` in the JSON). A path you wrote yourself is not scrubbed: an absolute path in `server.args` or `server.env` that points outside the sandbox (a memory file, a data directory) is a real file on your machine that valid calls may read or write, so `run` and `doctor` warn about each one and `init` offers `{sandbox}/<name>` instead. With `--no-sandbox`, or for a server Sealmark did not start in the sandbox (`--start` with `--url`), the server inherits your whole environment, and the packs that need the sandbox are `n/a`.
3. **Never put real credentials or real connection strings in `sealmark.yaml`.** The harness cannot know where a server actually connects. If the config hard-codes a real database URL next to a `{dsn}` placeholder, probes (including `DROP TABLE audit_probe`, `TRUNCATE probe_t`) could reach it. Use only the placeholders for database access.
4. **Core sends invalid input to up to 25 tools**, and one no-argument call to each read-only tool that takes none. See `robust-input` side effects. Use a sandbox configuration.
5. **Database probes only target `sealmark_seed`**, through the three seed roles, and the state reader connects as the harness's admin user. The probes create and drop only seed objects (`probe_t` contents, `sm_ddl_probe`, `audit_probe`).
6. **Embedded Postgres (default).** A real Postgres process started by the harness, bound to `127.0.0.1` on a free port, with a temporary data directory and a random admin password, stopped and deleted at the end of the run (and on Ctrl-C). It needs the `embedded-postgres` package, which installs a platform-specific Postgres binary package (an optional dependency). No Docker.
7. **`--pg <dsn>` runs administrative SQL on your Postgres.** With `--pg` the harness connects with the DSN you give it (only host, port, user, and password are used; the database in the DSN and parameters such as `sslmode` are ignored) and runs:
   - `DROP DATABASE IF EXISTS sealmark_seed WITH (FORCE)`, which **disconnects everyone connected to that database and destroys it**;
   - `CREATE ROLE` or `ALTER ROLE` for `sm_analyst`, `sm_support`, `sm_admin` (`LOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, **a random password generated for each run**). If a role of that name already exists its password and attributes are overwritten;
   - `CREATE DATABASE sealmark_seed`, then revokes `PUBLIC` access to it and grants `CONNECT` to the three roles;
   - `pg_terminate_backend` on any session connected to `sealmark_seed`.
   It needs a superuser (checked first, with a clear error) and refuses to run without `--yes`, so these effects cannot happen by accident. At the end of the run the harness makes a best-effort attempt to `DROP DATABASE sealmark_seed` and `DROP ROLE` the three `sm_*` roles again, **including any role of those names that existed before the run**. If the run is killed hard that cleanup does not happen, and the roles stay in the cluster, with a random password that was not written anywhere. Postgres lets `PUBLIC` connect to other databases by default, so use a throwaway or dedicated instance, never a shared or production one. The harness never touches other databases, but it cannot stop you pointing it at the wrong server.
8. **Cleanup.** Server processes, sessions, backends, the seed database and roles (for `--pg`), and the embedded Postgres are cleaned up in a `finally` block and on SIGINT, SIGTERM and SIGHUP (exit 130, 143 and 129). After a signal the harness closes the sessions, stops the server, waits up to three seconds for the running pack, starts no further server (the next database role is not started), removes the sandbox and the databases, abandons an embedded Postgres that is still starting (its data directory and password file are removed), sweeps a second time and, if a directory is still there, prints its path (`cleanup did not finish: <path>`). The harness remembers the server's process tree once the connection is up, so when a launcher such as `npx` or `uvx` exits before its child, the remembered descendants are still stopped (a process is stopped only if its command line still equals the remembered one, which guards against pid reuse). On Windows the harness also kills the server's whole process tree, because the MCP SDK kills only the direct child and an `npx` wrapper would otherwise leave the real server running; that Windows path is written but has not been run on Windows by the maintainer. The per-run sandbox directory is created with mode 0700 on POSIX. A hard kill (power loss, `kill -9`) can leave a temp directory and a Postgres process behind.
9. **Valid-looking input is only sent to harness-owned targets.** Tools classified with medium confidence or higher get probes that point at the sandbox, the loopback listener, the seeded database or a harness-owned program; a tool the harness could not classify is never given a well-formed argument. (It still gets schema-invalid ones in `robust-input`.) Prompt arguments are never probed: the harness lists prompts and scans their text but does not call `prompts/get`.
10. **Do not publish a result for a named server that shows a failure before the maintainer has seen it.** See `docs/product.md` (disclosure).

## What changed in 0.3-draft

0.3-draft is a methodology change, made so it can be accepted or rejected as one unit: the verification fixes, the owner decisions the project resolved by recommendation, and one regeneration commit at the end that rewrites the standard hash, the generated `standard.yaml` profile, `profiles.golden.json` and the JSON Schema together. The methodology string stays `0.3-draft` (unreleased). The standard hash (`cli/src/test/fixtures/config/standard.hash.txt`; it was `sha256:c2b6ce21…` under 0.2-draft) moved twice: first through the version string alone, and again in the final commit because **locked leaves changed**: the two settings of `net-redirect` (`checks.net-redirect.enabled` and `.severity`) became locked when it was promoted, and `retries.call` stopped being locked. A report written under 0.2-draft cannot be `--replay`ed under 0.3-draft, and a baseline written under 0.2-draft prints the "different configuration" note.

What can move a verdict or a grade is the probe corpus, the classifier, the check logic and the scoring of `net-redirect`. Each item below is covered by a synthetic toy server that exhibits the flaw and must now fail, and a near-miss toy that must still pass. Letters can change in either direction: a server that was passing because a probe never ran can now fail, and a server that was inconclusive because the harness did not recognise a refusal can now pass.

**Classifier (`classify.ts`).**
- Candidates are ranked by evidence strength first. A parameter with `format: uri` or `format: url` is a strong `url` signal and outranks a generic parameter plus a hint in the tool name; the fixed specificity order only breaks ties between equal-strength candidates. Before, a tool with a generic parameter name and the word "file" in its name was probed as a path tool, and the `net` pack never ran against it. When two candidates reach `medium` with equal strength, both are recorded.
- The words "git-style" (as in "git-style diff") in a description are no longer a `git` signal, so a path writer is not demoted to `core` only for that reason.

**`fs` pack.**
- Relative-path escapes (`rel-dotdot`, `rel-dotdot-fwd`, `rel-evil`) run for every tool whose relative control works, in addition to the absolute set. Before, a tool that accepted an absolute control path never received the relative probes, so a server that validates absolute paths but resolves relative ones unchecked passed `fs-read-escape` and `fs-write-escape`.
- Move and copy tools receive the canary in the source slot as well as the destination (`move-copy`, which the corpus listed but did not send). A server that validates the destination but not the source now fails `fs-write-escape`.
- A read tool that returns file content as base64 text (in a text block or in structured JSON) is controlled and probed: the harness decodes it before matching tokens. A real resource, image or audio content block is decoded as far as the 8 MiB-per-result cap allows (round 3; before, the client kept only a placeholder), so a tool that returns file content that way is controlled and probed: its control passes when the control token appears in the text or in a decoded block, and a canary in a decoded block is a leak. Only a block whose data was not carried (over the cap) leaves the tool unprobed and listed under "Not covered" with its own reason. A high-confidence read tool whose control could not be established makes `fs-read-escape` `part`, not a clean pass.
- `fs-read-escape` and `fs-write-escape` are `inconclusive` when no escape probe was answered (the zero-probe guard, round 3). When some were answered the verdict is judged on those and the summary says how many (`54 of 56 variants answered; 2 timed out`).
- `fs-link-escape` records one evidence line per link probe (a pass shows the link path was exercised) and runs a control through a link that stays inside the root. It is `na` when no tool reads or writes files, and `inconclusive` only when a control was attempted and failed.

**`git` pack.**
- `git-repo-scope` probes a sibling repository whose directory name has the configured repository's path as a prefix (`<repo>-evil`, with its own token). Before, the prefix probe targeted a sibling of the sandbox root, which a prefix-matching scope check never confused with the configured repository.
- `git-arg-injection` also injects into parameters declared with `anyOf`, `oneOf` or `$ref` that allow a string (an optional string parameter is typically declared that way). A string-capable parameter that is skipped is listed as not covered, and the "nothing to inject" text is no longer printed for a tool that has string parameters.

**`net` pack.**
- The size half of `net-caps` is judged by what the listener recorded, not only by the length of the reply. In 0.3-draft's first round a server that consumed the whole 64 MiB body and then returned a small reply was `part`; round 3 makes the byte count the rule: the size half is a fail when the listener sent the whole body and the server did not hang up (`the listener sent 64 of 64 MiB`), whatever it replied, and a pass when the server aborted early or consumed less and replied small. The measurement is described in the check's `falsePositive` text.
- `net-loopback-ssrf` recognises more refusal wording ("not a public address", "refused to fetch", "resolves to" with the resolved address, and a JSON-RPC invalid-params error that names the address). A fetch that merely failed ("fetch failed", unreachable) is still not a refusal. A correctly refusing server that was `inconclusive` for want of one word can now pass. The second verification round replaced the word list with a model (see "Round 4" below), and the third replaced the model's tiers (see "Round 5").
- A `data:` scheme probe that a tool accepts is `part` when the reply is an embedded resource, image or audio block whose decoded bytes contain the decoded `data:` content (round 3 reads the block; before, only a text marker was available, so the bytes were not inspected), or when a tool already shown to fetch answers it without refusing. A bare non-error reply from a tool that never fetched stays `inconclusive`.

**`sqlite` pack.**
- A declared writer tool is probed by `sqlite-file-write`, `sqlite-file-read` and `sqlite-extension-load`: `VACUUM INTO` and `ATTACH` to a path outside the sandbox are writes the file observer verifies, and need no read control. Before, a read/write-split server whose writer tool wrote arbitrary files passed `sqlite-file-write`. For `sqlite-file-write` and `sqlite-file-read`, any single tool that writes or reads another file now fails the check; before, a clean tool plus a leaking tool aggregated to `part`. A controlled writer that is still excluded from a check it could be probed for makes the check `part` or `inconclusive`, and its `falsePositive` note describes the (much narrower) exclusion.

**Round 3: the owner decisions, resolved by recommendation, and the code-only fixes that came with them.** The first seven rows, and the four decisions listed in the paragraph under the table, are owner decisions, implemented as their standing recommendation. Each is **decided by recommendation, owner may veto**; the veto path is in [`decisions.md`](decisions.md) (D14 to D24). The `robust-input`, corpus and content-block rows are verdict fixes in code that need no decision, listed because they move verdicts.

### Round 4: the second verification round

A second verification round ran the merged build against real public servers and re-checked every earlier defect. The fixes below are verdict-changing code inside the same unmerged 0.3-draft unit; none of them adds, removes or unlocks a locked setting, so the standard hash is expected to be unchanged (the methodology package confirms it when it regenerates the profile and the golden files; the one new hash input is described under "The configuration hash" and appears only for a run that has it). The design is `docs/round4-design.md`. Each change is covered by a synthetic toy server that must now fail or be inconclusive, and a near-miss toy that must still pass. No result for a named third-party server is recorded anywhere in this repository.

**The net refusal model (`net-loopback-ssrf`, `net-scheme-allowlist`). Round 5 replaced the tier list below; read "Round 5: the net refusal model" for the one that runs.** The harness owns one network target, its loopback listener, which is exactly what a correctly guarded tool refuses, so without `net.control_url` a pass has to rest on the responses. The principle: **a refusal is a declined reply that ties the refusal to the target.** A reply that only reports that a fetch failed, or names the mechanism that failed (proxy, socket, DNS, timeout), is a failure, whatever adjectives it uses. Each probe's reply is judged in this order:

1. A reply that is not declined (no `isError`, no JSON-RPC error) is `answered`. A timeout or a closed connection is `failed`.
2. The probe URL, in every spelling, is removed from the text first, so an echo of it cannot match anything.
3. **Strong target-class phrases** make it `refused`. They name the class of address that is refused, which a generic transport error never does: `loopback`, `link-local`, `private` with `address`, `ip`, `range`, `network`, `host` or `subnet`, `internal` with `address`, `ip`, `host`, `network`, `url`, `resource`, `service` or `target`, `reserved address`, `non-routable` or `not routable`, `not a public address`, `unsafe destination`, `ssrf`, `metadata endpoint`, `resolves to` an address, `refused to fetch`, `connect`, `request` or `follow`, and an allowlist statement (`only ... allowed`). For the scheme check the scheme words and phrases (`unsupported scheme`, `only http`) are strong too.
4. **The failure veto** makes it `failed`, and is checked before the generic tier: `ECONN*`, `ENET*`, `EHOSTUNREACH`, `ETIMEDOUT`, `EAI_AGAIN`, `ENOTFOUND`, `connection refused`, `reset`, `closed`, `failed`, `error`, `aborted` or `blocked`, `network is unreachable`, `timed out`, `proxy`, `socket`, `dns`, `name resolution`, `getaddrinfo`, `certificate`, `tls`, `ssl`. A strong phrase wins over the veto, so "connections to a private address are not allowed" is still a refusal.
5. **A generic refusal word and a target noun** make it `refused`: one of `blocked`, `not allowed`, `not permitted`, `forbidden`, `disallowed`, `prohibited`, `denied`, `rejected`, `refused`, `restricted`, `invalid`, `unsafe`, `bad request`, and one of `host`, `hostname`, `address`, `destination`, `target`, `url`, `domain`, `ip`, `origin`, `site`, both within the first 300 characters. "This URL is blocked" is a refusal; `connection blocked by proxy` and `network access is restricted in this environment` are not (no noun, and the first is vetoed).
6. **A structured validation error naming the address** is `refused` when the reply is declined (`isError`, or a JSON-RPC `-32602`), names a loopback address, is not vetoed and carries a refusal word. This is the form a Python SDK server uses when a handler raises an `McpError`, which arrives as an `isError` result and not as a JSON-RPC error.
7. Anything else is `failed`.

`net-loopback-ssrf` still passes when every probe was refused or a control fetch worked, and a tool that fetches nothing is `inconclusive` (the summary says that a reply that only reports a failed fetch is not read as a refusal). The evidence line for each probe names the rule that decided it: `explicitly refused (names the address class)`, `explicitly refused (refusal tied to the host)`, `explicitly refused (validation error naming the address)` or `failed without saying the target was refused`. A vocabulary miss is therefore visible in the report and arguable in a bug report. A correctly guarded server that was `inconclusive` for lack of a recognised phrase can now pass; a tool that cannot fetch anything and says "blocked" no longer passes.

**The corpus principle (net and fs).** One corpus entry per *normalisation family* a client library may apply after the server's own check, and only families a client can resolve. The loopback corpus has dotted-decimal, name, IPv6 loopback, shortened dotted, hexadecimal integer, decimal integer, the unspecified address, **IPv4-mapped IPv6** (`http://[::ffff:127.0.0.1]:{port}/...`, new in this round, which reaches the IPv4 listener through the IPv6 socket family and needs no separate listener), a same-origin redirect and the opt-in DNS name. Octal (`0177.0.0.1`) and the other `127/8` addresses are not in it: a client that reads octal as a host name fails to resolve it, which would turn a correctly guarded server inconclusive, and `127.0.0.2` is not bound on every platform. The `fs-write-escape` corpus **mirrors the read corpus** wherever a write can carry the same path form: forward-slash, dot-slash, percent-encoded (`{sandbox}/%2e%2e/canary/...`), `file://`, the Windows-only extended-length and case-variant forms, and a relative dot-dot with forward slashes; the move and copy destination probes gain a percent-encoded and a `file://` form (a `file://` source is covered by the read corpus). A server that applies a lexical root check and then decodes, or that strips a `file://` prefix after the check, now fails `fs-write-escape`.

**`net-redirect`.** A server that follows the same-origin redirect and refuses the redirect to a spelling it refused when given directly has shown that it re-validates the target, which is what the check is named for, so it now passes: "redirects are followed and the redirect to `<spelling>`, which the server refused when given directly, was not". A redirect that was followed to the refused spelling, a `file:` read or a raw TCP connection still fails, a server that follows nothing still passes, and `part` stays for the cases the probe cannot separate (every spelling accepted directly, the Host header did not show the spelling, or the hop could not be sent).

**Secondary classes and fillers.** A tool that is a `path` tool and also has a `url` parameter (`format: uri`, for example) is probed by the `net` pack as well, with the url slot filled by the probe and the other required parameters by their fillers. Only a secondary `url` is consumed: a secondary `path` or `git` would aim write probes at a tool whose primary slot then holds a harness token, which can only produce a vacuous pass, so those are listed under "Not covered". A required parameter declared as a boolean or a string gets `false`, because a boolean is a member of the union and a token is not (before, a token was sent and every control call of such a tool failed with an invalid-params error).

**The coverage rule.** A call counts toward the coverage level, "tools called with valid arguments" and the badge wording only when it was schema-valid **and** the server processed it. A control call counts when it succeeded. An escape or policy probe counts when the tool's control succeeded (the refusal is the behavior under test) and the reply was not a validation error (a JSON-RPC `-32602`, or an `isError` reply that names a parameter and says `invalid` or `expected`). A `net` probe whose outcome was a failed fetch never counts. A pack whose checks are all `inconclusive` or `n/a` contributes no valid calls, whatever it reported. Coverage is not a grade, but it decides the `hygiene only` label, so a run in which every control or probe errored cannot look covered.

**The git fixture and applicability.** Every fixture repository has a **staged change** (a second file, `staged.txt`, added to the index after the commit, so `git diff --staged`, `git status` and `git diff HEAD` all print the token), and the root repository holds an untracked **symbolic link** to the canary repository (`linkout`; on Windows a junction when one can be made). Commit dates are fixed, so commit SHAs repeat between runs. `git-repo-scope` aims every read tool at the canary repository, at the prefix sibling and through the link; a response carrying the canary token through the link is a leak. When a high-confidence read tool could not be judged because its control failed, the check is `part` and the summary names the tool; it is `pass` only when every read tool was judged. Write-capable tools were not aimed at other repositories in round 4; round 5 probes them by observation (see "Round 5"). **The `git` pack is not applicable without `{sandbox}` in the server config**, because a server given a real repository would reach every other repository legitimately and the critical check could not be configured; a pack graded on one check while its critical check is unmeasured by configuration would be a letter built on nothing, so it says what to add (`{sandbox}/repo` as the repository argument) and `doctor` prints the same reason. When no read-only git tool exists, `git-arg-injection` is `inconclusive`, not `n/a`, because the probes were sent. The `effects` pack uses the same argument filler as the git pack for a git tool, so a git tool is not counted as having "changed nothing" only because its control failed.

**The sqlite forms.** `sqlite-extension-load` decides from the engine's own words only: `attempted` (the loader was reached), `denied` (a not-authorised or disabled message that mentions loading or extensions, or an unsupported feature) or `unknown`. A server's refusal of the probe is not a denial. For each controlled tool the harness sends the SELECT form; when the reply is `unknown` and a refusal, it retries with the form the tool's role accepts: for a declared writer an `INSERT` and then an `UPDATE` whose value calls `load_extension`, for a reader a `SELECT ... WHERE load_extension(...) IS NULL`. A tool that refuses every form without saying anything about loading is `inconclusive`, never a pass. **`sqlite-file-read` follows the file-read through the reader.** When a declared writer's `ATTACH` returns no rows, the harness runs the read of the attached file through a controlled reader on the same session and then lists the attached databases: the canary token through the reader is a leak (the evidence names both tools), an alias that is not visible and a `no such table` means the ATTACH did not persist for the reader (a fresh connection per call, so `clean`), a visible alias whose read was refused is `clean` with a note, and no reader at all stays `inconclusive`.

**`fs-size-cap`.** When a high-confidence read tool's control failed and no read-kind control passed, the check is `inconclusive` ("the control call of `<tool>` failed, so a large read was not attempted"), not `n/a`; `n/a` stays for a server with no read tool at all.

**The configuration hash and explicit pack lists.** The ids of custom checks and the plugin modules enter `config.hash` only when there are any (an empty set is omitted, so a run without them keeps the published standard hash). A CUSTOM run with probes that carry a `check:` therefore has a different hash from a STANDARD run, and `--baseline` and `diff` say "different configuration". `custom` is appended to the pack list only when the list was not chosen explicitly: a list from `--pack` or `packs:` is used as written, and when it omits `custom` the probes are skipped with a warning in the report.

**Not changed this round, and why.** A single executed mutating-SQL form that is not a core case still earns `part` on `mutating-sql` with no cap, so a real bypass of an indirect form can grade C; which cases are core is an owner decision (D25 in `decisions.md`: promote `function-in-from`, `explain-analyze-write` and `prepare-execute-single` to core in a later bump, or keep them indirect). The stderr line and the summary now say `critical part` so it is not lost. Octal SSRF spellings, write-capable git tools aimed at other repositories, a harness-owned control URL, per-parameter single-fault `robust-input` variants and a `prompts/get` surface are deferred with reasons in the design document.

### Round 5: the third verification round

Two further verification runs followed round 4: a re-run of the original public servers against the round-4 build (211 earlier issues fixed, 51 still open, none regressed, 52 new) and a first run on twenty servers never used for testing. Their defects fall into a small number of root causes, fixed below as verdict-changing code in the same unmerged 0.3-draft unit, or as no-verdict-change fixes (cleanup, text, redaction, `init` and `doctor`, counting). No fix adds, removes or unlocks a locked leaf, so the standard hash is expected to be unchanged; the two new configuration keys are unlocked and enter the JSON Schema, not the digest. The design is `docs/round5-design.md`. Each verdict change has a synthetic toy that must now fail (or be inconclusive) and a near-miss toy that must still pass. No result for a named third-party server is recorded anywhere in this repository.

**Round 5: the net refusal model.** The principle is unchanged (a refusal ties itself to the target), but what it rests on moved from word lists to what the harness observed. The harness owns one network target, its loopback listener, which is exactly what a correctly guarded tool refuses, so without `net.control_url` a pass needs the replies; the replies are therefore judged in nine steps, in this order:

1. A timeout or a closed connection is `failed` (not declined: answered).
2. The reply is stripped of every spelling of the probe URL (as sent, `encodeURI`, `encodeURIComponent`) and of every `<listener host>:<port>` spelling (each corpus host spelling, bracketed and percent-encoded, followed by this run's listener port). Bare host names are not stripped: "cannot access localhost" is a legitimate refusal that names the address, and the failure veto separates it from an echo in a failure report.
3. The **failure veto** is read over the stripped text. It covers the transport words of round 4 and now `failed to (fetch|connect|load|download|resolve|reach|open)`, `(request|fetch|download|connection)… failed`, `refused to connect` (the phrase a browser transport prints for a dead port), `could not (connect|resolve|reach)` and `unreachable`.
4. A **rule phrase** is a refusal, "explicitly refused (names the rule)", and is tested before the veto on purpose: `ssrf`; `unsafe` with `destination`, `host`, `target`, `url` or `address`; `resolves to` an IP literal or to something private, internal, loopback, reserved or non-public; `only` or `just` with allowed, permitted, supported, accepted or "may be fetched"; `only` with public, external or internet; an egress policy, rule or filter; `failed validation` or `validation failed`; an invalid, unknown, unsupported or disallowed scheme or protocol; `supported schemes are`; `only http(s)`. "Request to a private address failed validation" carries `request … failed` and is a refusal.
5. A **class noun** is a refusal, "explicitly refused (names the address class)": loopback, link-local, a private address, IP, range, network, host or subnet, an internal address, IP, host, network, URL, resource, target or service, a reserved address, non-routable or unroutable, "not (a) public", non-public, a local network, address, host or resource, public hosts, addresses, URLs, IPs or domains, a metadata endpoint. It is not a refusal when the veto is true and the clause that holds the noun (split on a full stop, a semicolon or a line break) carries no refusal word once the veto spans are cut out, so `connection refused` cannot supply the word. "Connections to a private address are not allowed" stays a refusal; "Failed to connect to loopback interface: ECONNREFUSED" does not.
6. Otherwise the veto makes it `failed`.
7. A refusal word and a target noun in the first 300 characters is a refusal, "explicitly refused (refusal tied to the host)". The refusal words gain `can't access|reach|fetch|connect to` and `won't fetch|connect`, and `refused to fetch|request|follow` counts only here (it needs a target noun) and no longer on its own.
8. A reply that names a loopback literal and is a `-32602`, or an `isError` with a refusal, validation or cannot-access word, is a refusal, "explicitly refused (validation error naming the address)". The veto has already returned at step 6, so "Request for 127.0.0.1 failed: access restricted" never reaches this step.
9. Anything else is `failed`.

**The hostless twin.** The harness cannot prove reach without a URL the tool will fetch, but it can observe whether the tool's refusal depends on the target at all. When every loopback probe of a tool was refused, the listener saw nothing and no control fetch worked (the pass would rest on text alone), the harness sends that tool one extra call, `data:text/plain,sm-<token>`: a URL with no host. Both replies are compared as full texts after the same normalisation (the probe URL, the listener `host:port` spellings and the token removed, whitespace collapsed, case folded):

- **Rule 1, same text.** The twin's reply equals the reply of every refused loopback probe: the tool has one answer for everything and its refusals describe nothing, so the check is `inconclusive` ("every loopback probe was refused, but a data: URL with no host got the same reply word for word, so the refusal does not describe the target (the tool may refuse every URL; set net.control_url to a URL it can reach)"), code `net.ssrf-sametext`. This rule needs no vocabulary, so it closes a refuse-everything tool however it words its sentence.
- **Rule 2, address wording for a hostless URL.** The twin's reply differs but is itself a refusal at the class, host-tied or address tier for a URL that has no host: the wording is not describing the target either, `inconclusive`, code `net.ssrf-incoherent`, same hint.
- **Rule 3, coherent.** Otherwise (a scheme refusal, a validation error that names the scheme, a different generic error, or an answered reply the scheme check scores) the text-only pass stands: "all N loopback probes were explicitly refused (the response said so), the listener saw no request or connection, and a hostless URL got a different reply; no fetch of any URL was shown to work (set net.control_url to confirm the tool fetches)", code `net.ssrf-text-only`.

The honest limit: a guard that answers every rejection with one constant sentence, even a true allowlist guard, is `inconclusive` under rule 1 until `net.control_url` names a URL it fetches, because from outside it is the stub; most guards parse the URL, reject the scheme, then check the host, so their twin reply differs. This is the trade the round made: evidence the harness observed decides, and word lists only sort the replies that evidence has admitted. Refusal-only probes keep counting toward coverage (decision D33); whether a text-only pass should withhold the badge is the owner's (D29). A tool that answers a control URL is worded "the tool answered the control URL", because the harness cannot see a third-party fetch; a lookup tool that matches hosts against configuration gets the hint to settle it with `tools.overrides`. `net.control_url` is not used when it names a loopback, unspecified, `localhost`, IPv4-mapped loopback, private, unique-local or link-local address, and the report says so.

**`net-scheme-allowlist`.** "Refused for another reason (host guard, not the scheme)" explains nothing about the scheme: a pass needs at least one probe explicitly refused for the scheme (the rule phrases above, or the scheme words), or the tool shown to fetch (a listener hit in the SSRF check, or a control fetch); otherwise the check is `inconclusive` with the control-URL hint. The trivial-pass caveat is printed only when no probe was explicitly refused, and the count line reads "6 scored probes (javascript: is recorded, not scored)". A `data:` probe counts as decoded only when the token appears outside any URL-shaped run (`https?://\S+` and runs with a percent escape are removed first): an echo of the probe inside a slug is not decoded content.

**Tokens, `net-caps`, `net-redirect`, `http-cors`.** Every (tool, probe) pair has its own token, so one URL tool is never credited with another's listener hits. In `net-caps` a timed-out or JSON-RPC-error reply is "the call timed out before any reply; the cap could not be measured" (not a cap), "passed along and dropped by the transport" requires a listener record, and a reply lost to the 64 MiB message limit is `net.caps-dropped`, never "an error reply of 0.00 MiB". In `net-redirect` a server that accepts loopback targets directly and then follows the hop is `inconclusive` ("re-validation cannot be measured on a server that accepts loopback targets directly"), no longer `part` (D30); an IPv6 loopback hop target is added when the IPv6 listener exists. `http-cors` passes only when the HTTP control (a working `initialize`) succeeded; a `3xx` preflight makes it `inconclusive` ("the server redirected the preflight (Location: …); try the URL with a trailing slash").

**`tool-poisoning` and `protocol`.** The server instructions and the `serverInfo` fields are scanned (section 5.2); stdout noise and invalid tool results are `part` findings of `protocol` (section 5.1); `robust-input` reads a downstream failure as leniency and a runtime error as an internals leak, and adds nested variants (section 5.3).

**The classifier.** A string parameter whose normalised name ends in `path`, `file`, `filepath`, `filename`, `dir` or `directory` is a strong path parameter; a name starting with `destination`, `dest`, `target`, `to`, `output` or `new` makes it a destination and `source`, `src`, `from` or `input` a source. An array of enum values is filled with the first value, so a tool whose only unfillable parameter was an enum array is fillable. The classifier descends one level into an object or array of objects: a strong path key in `items.properties` makes the tool "would be path (param `files[].file_path`), but required parameter `files` cannot be filled by the harness" (unfillable, the reason printed, so `fs` reports `inconclusive` for it), and an object whose required sub-properties are all fillable scalars is fillable. A hint only in the tool description no longer promotes a generic parameter to medium: it must be in the tool name, the title or the parameter's own description.

**`sqlite`: the engine rule and the file forms.** After the first control read passes, the pack runs `SELECT sqlite_version() AS sm_v` on that tool. A reply carrying a `3.x.y` version confirms SQLite. Otherwise every check is `inconclusive` with "the server's engine did not answer like SQLite (`sqlite_version()`: <reply>); the sqlite corpus does not apply", and the engine an error names (`DuckDB`, `Catalog Error`, `Binder Error`, `Parser Error`) appears only in that reason text, never as the decision. A tool that refuses functions altogether proceeds as SQLite with the evidence note "engine not confirmed". The pack's n/a text, shown when the config has no `{sqlite_path}`, says it applies to SQLite servers only and that a DuckDB server is not graded in this release (`{duckdb_path}` is a placeholder only; see "Known blind spots"). The file checks now try several forms, because a fresh connection per call hides the two-call form:

- `sqlite-file-read`: the two-call `ATTACH` then `SELECT`; the single-call `ATTACH '…' AS a; SELECT v FROM a.secret`; and the copy-into-fixture form `ATTACH '…' AS a; CREATE TABLE sm_rd_<t> AS SELECT v FROM a.secret`, in one call and as two. The copy form is **verified by reading `sm_rd_<t>` from the fixture file directly** (`db-state`), which needs no reader and settles a declared writer that returns no rows. Any form that shows the token fails the check. An accepted `ATTACH` with every form showing nothing stays `clean` only when the alias is provably gone on the same session or the stacked forms were refused as multi-statement; when nothing can be observed it is `inconclusive`, because the absence of an error is not an observation.
- `sqlite-file-write`: `VACUUM INTO` and `ATTACH` of a new file, verified by the file observer (a file appearing outside the sandbox is the escape), now also reached through the DDL control below for a DDL-only tool. A declared read-only mode must cover these forms, not only INSERT, UPDATE and DELETE. Statements such as `COPY … TO` and `EXPORT DATABASE` belong to engines this pack does not grade (see the engine rule above).
- **The DDL control.** A tool whose SELECT and INSERT controls both fail gets `CREATE TABLE sm_ctl_<t> (x)`, verified in the fixture. A DDL-controlled tool runs the file probes behind a DDL prefix (`CREATE TABLE sm_p_<t> (x); ATTACH …; CREATE TABLE sm_rd_<t> AS SELECT …` for reads, verified in the fixture; `CREATE TABLE sm_p_<t> (x); VACUUM INTO '…'` and the `ATTACH`-create form for writes, verified by the file observer).
- **The part rule for an uncontrolled SQL tool (D31).** A SQL tool that answers none of the three controls makes `sqlite-file-read` and `sqlite-file-write` `part`, never `pass`, and the summary names it ("X could not be controlled, so the check cannot say it refuses"), as `git-repo-scope` does for a read tool.
- **`sqlite-rowcap`.** A limit message with zero rows is a cap on its own; an unrecognised zero-row reply that is not a refusal is `inconclusive` for that tool ("no rows and no recognisable limit message"), not a `fail`.
- The stacked tally reads "N blocked, M ineffective (accepted, only the first statement ran)", and the read-only `part` summary adds "see mutating-sql" when that check failed on the same tool.

**`db`: the terminator family and the required parameters.** The mutating-SQL corpus has 19 cases (section 6.4): `ROLLBACK`, `END` and `ABORT` join `COMMIT`, all core, each followed by an `INSERT` judged by `db-state`. `COMMIT WORK` and `COMMIT TRANSACTION` add nothing (same keyword), and `… AND CHAIN` keeps the read-only characteristic and is not an escape. A SQL tool with other required parameters is graded with them filled (section 6, "Other required parameters"), `sql_tools[].args` overrides the fillers, a DDL-controlled tool runs one more core case, and `write-gate` is computed after the corpus. The `sql_tools` paragraph of section 6 now describes what the code does (an explicit list adds or corrects, never hides).

**`git`: controls, relative targets, write tools, the part rule.** In this order, because widening "unjudged means part" before the controls are fixed would have created a wave of false fails:

1. *Controls the fixture can satisfy.* A parameter named `file`, `filePath`, `file_path`, or `path` (when the repository is another parameter) is filled with `tracked.txt` (a string) or `["tracked.txt"]` (an array); `object`, `commit`, `sha`, `hash`, `ref`, `rev` are filled with `HEAD`. The fixture has a remote, `sm-origin`, whose URL is the root repository's own path, and a tag `sm-tag-<root token>`, so remote and tag listings carry the root token. A reply that is a well-formed success with an empty list is reported as "answered but showed no repository content, so not judged", never as "did not answer".
2. *An unjudged read tool makes `git-repo-scope` `part` at any confidence*, and is named in the summary, which never cuts it. (Before, only a high-confidence tool did, and git tools are mostly medium.)
3. *Relative targets*, built through the same filler as the absolute ones and judged by the other repository's token: working-directory-relative `../canary/repo`, `../root-evil`, `repo-evil` and `repo/linkout`, and repository-relative `../../canary/repo`. A path that resolves to nothing is a git error with no token, so a correct server cannot fail on them.
4. *Write tools, judged by observation.* The control calls the write tool on `{sandbox}/repo` with harmless fillers (branch `sm-br-<t>`, message `sm`, files `["tracked.txt"]`, target `HEAD`, and a destination `{sandbox}/wt-<t>` for clone, worktree or init tools); a change under `{sandbox}/repo/.git`, or the destination appearing, is the control. The probe repeats the call with the repository set to `{canary}/repo` (a change under its `.git` is an escape), the destination set to `{canary}/wt-<t>` and to `{sandbox}/../root-evil/wt-<t>` (a directory appearing outside the root is an escape), and the clone source set to `file://{canary}/repo` (a clone whose files carry the canary token appearing inside the root is an escape). A write tool whose control changed nothing is listed as not judged and does **not** make the check `part`: the part rule is for read tools, whose refusal is the claim. The read-tool controls and probes run first; the fixture's `.git` directories (root and canary) are restored from a snapshot between the two halves, because a commit, reset or checkout control changes the staged file, `HEAD` and the tag the read controls rely on. Every repository involved is harness-owned.
5. *Wording.* `git-arg-injection` with no qualifying tool says "no read-only git tool exists to make a control call".

**`effects`.** A URL tool whose control fetch was refused is `n/a` when the `net-loopback-ssrf` result in `ctx.prior` is a pass with every probe refused ("the tool refuses loopback targets (net-loopback-ssrf passed), so no harness-owned control URL exists"); when every subject is `n/a` the check is `n/a`. So under the `ci` profile, which fails an inconclusive pack, **a correctly guarded URL tool can be green**: `effects` is `n/a` for it, where before it went inconclusive after `net` passed and the pipeline could never be green. A tool with no required parameters and `readOnlyHint: true` gets `{}` as its control, observed like any other, and a lying no-argument tool fails `annotation-honesty`. The pack runs when any usable tool is annotated or an unannotated read-style tool exists; `annotation-honesty` and `openworld-honesty` are `n/a` when nothing is annotated, and `undeclared-writes` still runs.

**`fs`: more families, edit tools, search controls, rootless servers.**

- *Corpus.* `array-second` (for array path parameters, `[<control>, <escape dotdot>]`: the escape in the second slot); `backslash` (`{sandbox}\..\canary\<leaf>`, sent literally on POSIX, where it is one file name inside the sandbox directory, so a server that normalises `\` to `/` after its root check fails) and `rel-backslash` (`..\canary\<leaf>`); `evil-dotdot` joins the write corpus. Move and copy probes gain `move-dest-link` (destination under `{sandbox}/link-dir`, observed in the canary) and `move-src-link` (source `{sandbox}/link.txt` with the destination inside the root: the destination holding the canary token is exfiltration; a moved link is not). Link probes gain `link-file-write` (a write through `{sandbox}/link.txt`; the canary file changing is the escape) and `dangling-link-write` (`{sandbox}/link-dangling.txt` pointing at `{canary}/dangling-<t>.txt`; the file appearing is the escape). On Windows the backslash forms coincide with `dotdot` and are sent once. A link to a directory is a "symbolic link to directory" on POSIX and a "junction" on Windows.
- *Edit tools.* A tool whose verb is `edit`, `patch`, `modify`, `str_replace`, `replace_in` or `apply_diff` is a kind of its own. Its control edits `{sandbox}/ok.txt`, replacing the control token with a new one (observed: `ok.txt` changed); its probes are the write corpus paths aimed at existing outside files, replacing the canary token (observed: the canary file changed). The arguments are built for the common shapes (`edits: [{oldText, newText}]`, `old_str`/`new_str`, `search`/`replace`, `old_text`/`new_text`). A tool that needs a content hash fails its control and is listed with "requires an existing file and a content hash".
- *Verbs.* `export` and `dump` are write verbs and `import` and `load` read verbs; the verb is taken from the tool name first and, from the description, only after parenthesised text is removed; a name that says `set`, `configure`, `default`, `cwd` or `chdir` with no other verb is `other` (a state setter is never a reader).
- *Search controls.* The filler is tried in order: no pattern, `ok` (substring or regex), `*ok*` (glob), `*`; the first that lists `ok.txt` wins. A tool whose every attempt fails with a regex-parse error is listed with "the control pattern was rejected as a regex", and a control failing with "command not found" or exit 127 says a dependency of the server is missing.
- *Applicability.* `fs-read-escape` is `inconclusive`, not `n/a`, when a reader exists but every control failed or its only reader is unfillable (the reason names the parameter, for example `files[]`). `fs-size-cap` is `inconclusive` when content readers exist and their controls failed, and `n/a` only when no content reader exists, so a search-only server no longer gets the wrong reason; its evidence says "the reply exceeded the harness's 64 MiB message limit (the server sent no cap)" when the transport reports that, and "the server exited" when the process is gone.
- **`server.rootless`.** `server.rootless: true` (unlocked, default `false`; D32) tells the pack that the server takes no root argument: its working directory, `{sandbox}`, is the allowed root, every probe runs, and the pack line says "root: the server's working directory (server.rootless)". The grade is honest: a server that reads and writes any path fails the escape checks, which is what it does. Without the key, a rootless path server prints the hint that suggests it.

**The coverage rule (no verdict change).** A call counts toward the coverage level, "tools called with valid arguments" and the badge wording only when it was schema-valid and the server processed it. Round 5 closes three ways a call that exercised nothing was counted: a reply that reports a failed upstream request without `isError` (the failed-fetch vocabulary), a schema-validation rejection, and an errored control call; a `probes:` valid call whose reply is a refusal in plain text does not count either, and `custom` checks apply the same rule. A refusal-only probe of a guarded tool still counts (D33). The `fs` and `git` packs count a control when it succeeded and a probe when its tool's control succeeded and the reply was not a validation error (`-32602`, or an `isError` that names an argument: "invalid, required, must be or expected" near "argument, parameter, field or input"). The counting fixes do not change a letter, verdict or badge: `badgeFor` reads the integrity record, the pack statuses, the provisional flag and the critical inconclusive checks, never `coverage.level`; only the `covered`, `low` and `hygiene only` label moves.

**Interrupts and the shared-memory segment (no verdict change).** A signal while the embedded Postgres starts now finds the start in a registry (`pending` until the handle is returned, then `live`), stops it with a kill ladder (SIGINT, 2 s; SIGQUIT, 1 s; SIGKILL last), reads the segment id from line 7 of the data directory's `postmaster.pid` and runs `ipcrm -m <id>` if the segment survived, so repeated interrupts no longer exhaust the machine's shared-memory segments. The whole cleanup is bounded at 12 s and the 15 s bail prints `cleanup did not finish: <dir> (remove it by hand)` before exiting. A run stopped by a signal ends with `sealmark exit 130: interrupted` and `RunResult.interrupted`, even when the signal lands as the last pack finishes. See `architecture.md` sections 4 and 7.

**Redaction and report fields (no verdict change).** Run tokens are redacted in every position (a `-abs`, `-rel` or `-<digits>` suffix and a `.txt` or `.db` extension no longer protect one: `w-ctl-sm-<hex>-abs.txt`, `w-sm-<hex>-3.txt`; `sm-control-<hex>`; `pwned-<hex>`; a 40-hex commit id and a `<7hex>..<7hex>` range become `{sha}`), the sandbox path in a truncated echo, the `file://localhost/<dir>` form and the `%2F` and `%5C` forms; `config.path` is stored relative to the working directory; JUnit properties and SARIF run properties carry the run warnings. Determinism is therefore true as stated: text, markdown, summary, badge and shields output is byte-identical at every verbosity, and the JSON differs in exactly three harness fields (`startedAt`, `durationMs`, `sandbox.listenerPort`). `--replay` of a run whose `custom` pack was auto-added runs it again with the user's own probes (a packs list from the replay layer is not an explicit list), and the hash stays what the report had.

**Not changed this round, and why.** DuckDB and MySQL grading (native or service dependencies a toy cannot run honestly; the sqlite pack now says so instead of grading a DuckDB server), octal and `127.0.0.2` SSRF spellings, a harness-owned public control URL (the only harness-owned target is the loopback listener, which a guarded tool refuses by design, so the hostless twin is what the round adds instead), a `file://` clone-source probe in the net pack, argument and shell injection into subprocesses of path and text tools, state written into a server's installed package directory, `prompts/get`, and the owner decisions D25 (which mutating-SQL cases cap the grade) and the badge rule for a text-only SSRF pass.

### Round 6: policy-heavy servers (candidate packs)

Everything is verified by observation, as before; the new observers are a harness-owned **upstream stub** (an HTTP server on loopback that the server under test uses as its backend through `{upstream}`, which records every request and answers with scripted replies) and the **server log** (what a server Sealmark started, or a stdio server, printed).

Identities: `{bearer}` (or `{bearer:a}`, `{bearer:b}`) in `server.headers` gives each session a caller token; the harness mints `sm-bearer-a-<hex>` and `sm-bearer-b-<hex>` per run, and `identities.a` / `identities.b` replace them for a server that validates tokens it did not issue (a server that refuses the minted ones leaves `upstream-credential` inconclusive with that advice). Rules: `probes:` gains `identity`, `matrix`, `cases`, `upstream.reply` and `expect.upstream`, `expect.log` and `expect.response.max_bytes` (the clauses are in the custom-probes guide); a probe may send SQL to a SQL tool when an upstream stub is declared, because the stub is the only backend the server then has. A probe with a `check` still makes the run CUSTOM.

Coverage: a candidate pack's calls count by the existing rule (a control that succeeded, a policy probe on a controlled tool whose reply was not a validation error); a tool a candidate pack probed is not reported as "covered by the core checks only".

Determinism: a run with a stub has a second ephemeral port and two minted tokens. Both are rewritten under redaction (`{upstream_port}`, `{bearer:a}`, `{bearer:b}`, and the corpus tokens), so the JSON differs between two runs in four harness fields when a stub ran (`startedAt`, `durationMs`, `sandbox.listenerPort`, `upstream.url`), plus the measured time of each valid call (`probes.calls[].elapsedMs`) when `probes:` are declared.

Launched HTTP servers: a server Sealmark starts (`server.command` with `server.url`) now runs inside the sandbox like a stdio server (working directory, scrubbed environment), so `fs`, `git`, `sqlite` and `effects` apply to it. Their verdicts can differ from a stdio twin when the server keeps per-process state: every pack session over HTTP is a fresh MCP session on the one process.

## Known blind spots

These are not tested by methodology 0.3-draft. A grade says nothing about them, and every text report lists the relevant ones under "Not covered".

- **Output-side prompt injection.** The harness scans tool, prompt and resource *metadata* for injection, not tool *results* (it would need a model in the loop, which is excluded by principle). A server that returns attacker-controlled text (a web page, a database row) is not tested for whether it can steer a model.
- **Authentication flows, authorization, and supply chain.** The `http` pack checks origin validation, whether the credential you configured is actually required, protocol version, sessions, CORS, bind address and TLS for an endpoint you point it at. Nothing checks login flows that need real credentials, OAuth, or whether an HTTP server is exposed beyond what those checks see. Package provenance, dependency vulnerabilities, install scripts, and update behavior are out of scope.
- **HTTP secret canary.** The secret-echo canary needs the harness to start the server with a modified environment, so for an HTTP server Sealmark did not start (a bare `--url`), `secret-echo` is `na`.
- **Audit logging.** Whether calls are logged, and whether logs hold sensitive data, is not measured (`audit` is advisory and `na`).
- **Non-Postgres, non-SQLite databases.** MySQL, DuckDB (`{duckdb_path}` is a placeholder only), SQL Server, warehouses, and NoSQL are not covered. The `db` corpus and seed are Postgres-specific; `sqlite` has its own, and it confirms the engine with `sqlite_version()` before grading: a server that answers like another engine is `inconclusive` on every check, never graded, and the pack's n/a text says SQLite servers only. Engines such as DuckDB can read and write arbitrary files (`COPY … TO`, `EXPORT DATABASE`, file-reading functions); no pack tests this, and the report says so when a SQL tool exists and no engine pack ran.
- **Redirects from a public host to loopback, and DNS rebinding.** The harness contacts only its own listener and owns no DNS, so `net-redirect` tests redirects the listener serves, not redirects an external host serves.
- **SSRF spellings beyond the corpus.** Octal (`0177.0.0.1`) and the other `127/8` addresses are not probed (a client that reads octal as a host name would turn a correctly guarded server inconclusive, and `127.0.0.2` is not bound on every platform), so a server that refuses every listed spelling but fetches an unlisted one passes. Private and link-local ranges are never contacted by design.
- **Write-capable git tools whose control cannot be observed.** `git-repo-scope` aims a write tool at the canary repository and outside destinations only when its control call on the fixture repository changed something the observer can see; a write tool whose control changed nothing is listed as not judged (it does not make the check `part`, because its claim is not a refusal), and the pass summary names it.
- **A refusal that rests on text alone.** Without `net.control_url`, the harness cannot see a tool fetch. A text-only SSRF pass rests on the refusal wording and on a reply that differs for a URL with no host; a guard that answers every rejection with one constant sentence is `inconclusive` until a control URL is set.
- **Probe values sent to a server's own upstream.** A URL tool may relay the harness's probe values (a token, a loopback address) to the service it wraps; the harness does not see that. `tools.exclude` keeps a tool out of the `net` pack.
- **Writes outside the observed directories.** The `effects` pack sees changes in the sandbox directories. A write to your real home, or to a store named by an absolute path in `server.env` or `server.args`, is not observed.
- **Tools listed only to clients that declare roots, sampling or elicitation.** The harness declares none, so such tools are not seen; every report says so.
- **Servers that need valid-looking arguments.** The harness will not guess valid inputs for tools it cannot classify. Tools it cannot classify with medium confidence or better receive only schema-invalid probes (plus a no-argument call for a read-only tool that takes none). A server whose only behavior sits behind valid calls it cannot build is graded on hygiene alone.
- **Tools beyond the first 25, and tools with untyped arguments.** `robust-input` probes the first 25 tools, and only arguments that declare a type. If it makes no call, `secret-echo` has nothing to scan and is `inconclusive`.
- **Only the default configuration you pass.** A server with a read-only flag, a row-limit flag, or an allow-list is graded as configured. Different flags can give a different grade.
- **Behavior under load, concurrency, and long sessions**, state carried between calls, and multi-user servers that authenticate callers some other way than the connection string.
- **Policy shapes beyond the seed.** One tenant-column policy and one column grant are tested. Other RLS designs, views, and functions are not.
- **Resources, prompts, sampling, and other MCP features** beyond `initialize`, `tools/list`, and `tools/call`. Prompt and resource text is scanned for poisoning indicators, but `prompts/get` is never called, so prompt arguments are not probed (deferred: it needs a methodology decision on a prompts surface).
- **What a model does with the tools.** There is no LLM in the loop, so agent behavior (jailbreaks, tool-choice errors) is outside the test.

## Candidate checks

A grade is a methodology, so a new scored check changes what an A means for every server. A check that is not yet part of the published standard therefore ships as a **candidate**:

- In a standard pack it is **advisory** (a check of a candidate pack is scored inside that pack instead, see "Candidate packs" below). It runs by default, appears in every report (a line ending `(advisory, not scored)`, one JUnit test case, one SARIF rule, one entry in the JSON `checks`) and is never counted in a grade, whatever its verdict.
- Its two settings, `checks.<id>.enabled` and `checks.<id>.severity`, are **not locked**, so the standard profile, `standard.yaml` and the standard hash (`config.hash`) do not contain it. A STANDARD run with a candidate present has the same letters, the same points, the same `config.hash` and the same `badge.eligible` as before the candidate existed. A baseline comparison treats a new check as never a regression.
- Turning a candidate off (`enabled: false`) or scoring it (`severity: scored` or `critical`) makes the run CUSTOM, with the difference listed, exactly as for any other check. A report's locked settings never carry a candidate's settings, so `--replay` leaves them at their defaults.
- `sealmark describe --json` marks it `candidate: true` and `standardLocked: false`.

The candidate checks in 0.3-draft are **`db-privilege`**, in the `db` pack (section 6.8), the two `core` advisories of round 6, `refusal-quality` and `instructions-hygiene`, and the checks of the three candidate packs below. It asks whether each of the three server instances connected as exactly the role it was given, and with what attributes, and it is advisory because scoring it would add a near-automatic point to every db grade (decided by recommendation, owner may veto; veto path: remove the registration, or score it at a later bump).

**`net-redirect` was the first candidate and is promoted.** It was added in 0.2.1 as an advisory candidate. 0.3-draft promotes it (decided by recommendation, owner may veto) to a scored, **not critical** standard check in the `net` pack: `candidate: false` in `config/schema.ts`, `advisory: false` in `packs/net-redirect.ts`, its `since` unchanged (`0.2-draft`), and its two settings locked, which is why the standard hash moved. It asks, with a loopback listener the harness owns, whether a URL tool follows a redirect, whether it re-validates where the redirect leads (a redirect to a spelling it refused when given directly) and whether it follows one to a `file:` or raw-TCP URL. It is `n/a` unless the server already fetched the listener, so it scores only servers that already fail the critical SSRF check, and `n/a` leaves the denominator. It does not test redirects from a public host to loopback or DNS rebinding. Veto path: `candidate: true`, `advisory: true` (a hash regeneration).

### Candidate packs

Round 6 adds a second kind of candidate: a **candidate pack** (`scope`, `sql-guard`, `upstream`; `CANDIDATE_PACKS` in `types.ts`). It is outside `STANDARD_PACKS`, and the run adds it to a pack list nobody chose when its declaration exists (`scope` when `scope.tools` is not empty, `upstream` when `upstream.kind` is set, `sql-guard` when it is set and a SQL tool exists), with the note "<pack> was declared in the config, so the pack is included"; a list you chose that leaves it out skips it and says so. Its checks are **scored inside the pack** (each pack gets its own letter) but the pack is labelled "candidate pack: not part of the standard profile" in every report and is never what makes a run badge-eligible. Its leaves are unlocked and follow the candidate rule: declaring a scope, a stub, identities or valid-call probes adds coverage and keeps a run STANDARD; switching a candidate check off or re-scoring it makes the run CUSTOM. Promotion follows the path below, plus adding the pack to `STANDARD_PACKS`.

### How a candidate becomes part of the standard

Promotion is a methodology change, so it belongs in a methodology bump, made by the owner in one commit. This is the path 0.3-draft took for `net-redirect`:

1. In `cli/src/config/schema.ts` set `candidate: false` for the promoted check ids and remove them from `CANDIDATE_CHECKS` in `cli/src/config/integrity.ts`. Decide in the pack's `describe()` whether the check stays `advisory` and whether it is `critical`.
2. Apply the other methodology items the owner has decided to make in the same bump (round 3 resolved all of them by recommendation, see "What changed in 0.3-draft").
3. Set `METHODOLOGY` in `cli/src/config/model.ts` to the new version (`0.3-draft` is unreleased, so a change that lands before 0.3-draft is accepted keeps the string and only moves the hash).
4. `cd cli && npm run build && npm run gen:standard`.
5. Run the tests. The integrity test prints the new standard hash; write it to `cli/src/test/fixtures/config/standard.hash.txt`, and update `profiles.golden.json` and the pinned check ids in `dead-code.test.ts` if ids moved.
6. Write a changelog entry that lists every change that moves a grade.
7. Say in the docs that a report from the previous methodology cannot be `--replay`ed (the methodology version and the locked settings are part of the hash) and that a baseline written under it prints the "different configuration" note.

The candidate rule in `integrity.ts` stays for the next candidates. What the owner can still decide later: scoring `db-privilege`, and whether drift ever becomes a scored check (a pinned surface would be a locked setting, `drift.pin`).

## Versioning and changes

- The methodology version (`0.3-draft`) and the harness version are recorded in every result.
- Until 1.0 is published the probes, thresholds, and formula may change without notice, and results from different methodology versions must not be compared.
- Any change to a probe, threshold, or the formula after 1.0 will bump the methodology version and be listed in the changelog.
