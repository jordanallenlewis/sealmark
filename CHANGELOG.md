# Changelog

What changed in each CLI release and methodology draft (until 2026-11-10 these notes opened the README). The full, per-check record of every change that can move a verdict is in [`docs/methodology.md`](docs/methodology.md), "What changed in 0.3-draft". Releases: [GitHub Releases](https://github.com/jordanallenlewis/sealmark/releases) and [npm](https://www.npmjs.com/package/sealmark?activeTab=versions).

## Next CLI release (unreleased)

- **`run --trace <file>`.** Writes the JSON-RPC wire log of the run: the messages the MCP client sent to the server and received from it, in order, as JSON Lines with the session each belongs to. It is redacted like the report (secrets, JWTs, sandbox paths and per-run ports; nothing with `--no-redact`), capped at 32 MiB (a last line says how many messages were dropped), and written for a failed start too. The `http` and `oauth` packs' own raw HTTP requests and non-JSON-RPC stdout lines are not in it. Off by default; no check, verdict or grade changes.
- **`run --trace`: each check names its sessions.** With `--trace`, a check in the JSON report carries `trace.sessions`: the MCP server sessions its own test area opened, which are the `session` values of that area's lines in the trace file. It is where to start reading, not a full list of what the verdict used: `refusal-quality` names none because it reads every test area's evidence; a check that also reads another area's results (effects reads the net results) names only its own area's sessions; the `http` and `oauth` packs send raw HTTP and open no session, so their checks name none; and once the trace reaches its 32 MiB cap, a later session can have no lines. Without `--trace` the report is unchanged. No check, verdict or grade changes.
- **`run --trace`: evidence points to its requests.** With `--trace`, a piece of evidence in the JSON report whose tool and arguments are exactly what was sent carries `trace.calls`: each `tools/call` request in the check's own sessions with that tool and those arguments, as `{session, request, response}`, where `request` is the request's `seq` line in the trace file and `response` the line of its reply (absent when the trace kept no reply, or when the harness cancelled the request after a timeout, even if a reply came later). It is a match on content: when the same call went out more than once in those sessions every one is listed (at most 10, then `more` counts the rest), and the sessions of different database roles or identities are not told apart, so it does not say which of identical requests the evidence came from. Not linked: evidence that names no tool or no arguments (summaries, static scans, `--verbosity verbose`'s per-call `robust.call` lines, which name the tool only in their text); evidence whose arguments are shown differently from what was sent: the `fs`, `git`, `effects` and `sqlite` packs show sandbox paths and canaries as placeholders (`{sandbox}/...`, `{canary}`), so their absolute-path probes are not linked, `sqlite` evidence that covers several calls and the `exec` pack's injection evidence show a summary, and a custom probe keeps its `{...}`; `refusal-quality`; the `http` and `oauth` packs' raw HTTP; and requests past the 32 MiB cap. Without `--trace` the report is unchanged. No check, verdict or grade changes.

- **`sealmark badge`.** Prints README snippets (Markdown, HTML, reStructuredText) for a badge: `--id <id>` for the sealmark.dev badge of a server the public fleet grades (flat, `--variant card` or `shields`; the same strings as the results page's copy buttons; the image exists only while that server's latest fleet run earns a badge, otherwise it is a 404), or `--svg <path|url> [--link <url>]` for a self-reported badge you committed (alt text `Sealmark (self-reported)`). `--json` prints `sealmark.badge-snippets/1`. It reads no report, fetches nothing and writes nothing. No badge rule, check, verdict or grade changes.
- **GitHub Action: badge outputs.** New inputs `badge` (`auto` by default: for a run sure to grade one server, `start` or `url` without `config` or a `--server <name>`, the action also asks for `--format badge,shields`) and `badge-id`. New outputs `badge` and `shields` (the file paths; old badge files in the report directory are removed before the run, so they always belong to this run), `badge-text` (what this run's self-reported badge says), and `badge-markdown`, `badge-html`, `badge-rst` (the sealmark.dev snippets for `badge-id`); the job summary gains a `### Badge` section. The badge files come from the CLI's existing formats, so this works with the pinned 1.0.1. No badge rule changes.
- **`sealmark inspect`.** Starts one server the way `run` and `doctor` do (sandbox as working directory, scrubbed environment), lists its tools, calls one with the arguments you give and prints the reply with what the harness's observers saw during that call: files added, removed or changed under the sandbox directories, requests that reached the harness's loopback listener, processes started under the sandbox, and the server's stderr. `--call <tool> [--args <json>]` makes one call and exits; without it the tools are listed and `call <tool> [json]` lines are read from stdin (a terminal or a pipe). `--json` prints one `sealmark.inspect/1` object per line. It grades nothing and runs no check: the call is the one you typed. The output names what is not observed (database effects, requests to anywhere but the harness listener, anything outside the sandbox) and, for a server that runs outside the sandbox, says nothing was observed rather than that nothing happened. Refuses a configuration that needs a database (`{dsn}`), a stub upstream or identity tokens (`{upstream}`, `{bearer}`) or the stub token issuer, because a made-up value would make the replies mislead. A write that arrives later than a short settle window after the reply shows under the next call, and a process that started and exited during a call is not seen; both are listed as not observed. No verdict, check or grade changes.

- **`sealmark install-check <server>`.** Before installing a server, prints the grade sealmark.dev's public fleet gave it (test areas, how much of the server the grade covers, the version and date tested, the Sealmark version, a withdrawn grade or a failed re-test, in the results page's words, and which lookup key matched) and the client config that starts the graded version: an `mcpServers` JSON block and a `claude mcp add` line, with the values to replace where the test run used a throwaway database or folder. `<server>` is an npm or PyPI name, a GitHub repository, a sealmark.dev results URL or id, or a prefixed key, normalised as the site's `/data/v1/lookup.json` documents; a name that several graded servers share lists each. The config follows the results page's rule and gives the same text (checked against all 270 public servers): a stdio server started by a plain `npx` or `uvx` line that pins the graded version, nothing while the page withholds the start command, and in the CLI also nothing when a word has a character outside printable ASCII. Every string from the data is made inert before it is printed. It reads `https://sealmark.dev/data/v1/` (or `--data-url`), starts, grades and writes nothing; exit 3 when the server is not in the public results, 4 when the data cannot be read (no grade is shown, never a guess). `--json` prints `sealmark.install-check/1`. No check, verdict or grade changes.

- **HTTP+SSE transport.** `--transport sse` (`server.transport: sse`, also under `servers.*`) tests a server on the older HTTP+SSE transport (protocol version 2024-11-05): `--url` points at its event stream, usually `/sse`, and the configured headers go on the stream's GET and on every POST. Streamable HTTP stays the default, and a config that names `streamable-http` reads exactly like one that does not. Under `sse` the `http` and `oauth` packs are not run, with the reason in the report (their raw requests assume a Streamable HTTP endpoint, so a verdict would describe nothing); the JSON report adds `server.httpTransport: "sse"` only for such runs, so other reports are unchanged. If the event stream drops, the session ends with it (calls come back closed, naming the cause) and is never reopened, since a new stream would be a new session that never saw `initialize`. `--start` waits for an SSE server with a GET; `doctor` reports the skipped packs the same way. `init` writes `transport: sse` for a client config entry of type `sse` (it used to warn that the server may not answer). A URL that answers the way the other transport does gets a new start-failure kind, `transport-mismatch`, with the flag to change. No check, probe, threshold or locked setting changes, so no grade moves and the standard hash stays the same.

## Methodology 1.0 (2026-11-14, ships with the next CLI release)

The methodology is published as 1.0. It is the 0.3-draft methodology with no change to any check, probe, threshold or the grading formula, so no grade moves for a given server. The version string changes, and the standard hash with it (`sha256:d13e7893…` to `sha256:2bea0fff…`): a report or baseline written under `0.3-draft` cannot be `--replay`ed under 1.0 and prints the "different configuration" note. From 1.0 on, any change that can move a verdict bumps the methodology version and is listed here. Candidate checks (the `oauth`, `scope`, `sql-guard` and `upstream` packs, `db-privilege` and the round 6 and 7 advisories) stay outside the standard. [`docs/methodology.md`](docs/methodology.md), "What changed in 1.0".

## CLI 1.0.1 (2026-11-11), methodology 0.3-draft

No change to any check or grade. A server that cannot start now gets a typed start failure (`dependency-resolution`, `needs-credentials`, `missing-runtime`, `bad-launch`, `initialize-timeout` or `unknown`) with one line of advice, printed next to the existing error and added to the JSON report as an optional `startFailure: {kind, advice}`; the error text, exit code 4 and `hint` are unchanged. The npm package no longer ships ten stale `dist/* 2.js` modules (Finder copies committed with 0.3.0), a port-in-use error now carries a hint, and `--help` has examples. Methodology stays `0.3-draft`.

- **Opt-in usage counter.** `SEALMARK_TELEMETRY=1` sends one anonymous ping per command (version, command, Node major, OS family, CI flag); off by default, `DO_NOT_TRACK=1` always disables it. The README's "Usage counter" section lists exactly what is sent.
- **GitHub Packages mirror.** Each release is also published to GitHub Packages after npm; npm stays the primary registry and nothing changes for `npx sealmark`.
- **Dependencies.** Lockfile updates only (hono 4.13.18, @hono/node-server 2.1.8, body-parser 2.4.0, qs 6.17.1, ip-address 10.7.6, fast-uri 3.1.9, zod 4.6.7, @modelcontextprotocol/sdk 1.32.2, @types/node 26.6.6); `npm audit` reports 0 vulnerabilities. No check or grade changes.

## CLI 1.0.0 (2026-11-09), methodology 0.3-draft

The version bump only: package, lockfile and the pinned version in the action and examples. Methodology stays `0.3-draft`, unchanged from CLI 0.3.0. The CLI version and the methodology version move separately; a methodology change is what can move a grade.

## Methodology 0.3-draft (CLI 0.3.0, 2026-11-04)

It is one methodology change, regenerated in one commit so it can be accepted or rejected as one unit (see [`docs/methodology.md`](docs/methodology.md), "What changed in 0.3-draft"):

- **Verdicts:** `net-redirect` is a scored, non-critical standard check. `tool-poisoning` flags terminal control characters (ESC, NUL and C1 strong; other C0 controls and DEL weak). `fs-read-escape` and `fs-write-escape` are inconclusive when no escape probe was answered. `exec-timeout-cap` confirms a "killed" reply against the process table. A refused no-argument call no longer counts as a valid call. The `db` mutating-SQL corpus has 19 cases (the transaction terminators `COMMIT`, `ROLLBACK`, `END` and `ABORT` are all probed), and the advisory candidate `db-privilege` checks that each instance connects as the role it was given.
- **Exit policy:** the `ci` profile counts an inconclusive pack as failing, and a provisional `A*` does not meet `--fail-under A`.
- **Reports and config:** one tag per check line (advisory checks end with `(advisory, not scored)`), one score fraction (points over scored checks) in every format, `{listener_port}` in the text sandbox line, and `sealmark config show` opens with `# STANDARD` or `# CUSTOM`. `retries.call` is accepted and ignored.
- **Second verification round (the same unit):** `net-loopback-ssrf` and `net-scheme-allowlist` accept a refusal only when it ties itself to the target (a reply that only reports a failed fetch, such as a proxy, socket or DNS error, is not a refusal), and the loopback corpus gains an IPv4-mapped IPv6 spelling. The `fs-write-escape` corpus mirrors the read corpus (percent-encoded, `file://` and dot-slash forms). The `git` fixture stages a change and plants a link, and the `git` pack needs `{sandbox}` in the config, like `fs`. `sqlite-extension-load` retries with a form the tool accepts, and `sqlite-file-read` follows a writer's `ATTACH` through the controlled reader. Coverage counts only calls the server processed (a reply that reports a failed upstream request, a schema-validation rejection and an errored control call do not count). A run with custom checks or plugins gets its own `config.hash`. A resolved package version is reported as `unknown` rather than guessed.
- **Third verification round (the same unit):** a refusal now rests on what the harness observed more than on words. A transport failure such as "refused to connect" is never a refusal; a tool whose loopback probes were all refused with nothing observed behind them is also sent a URL with no host, and if that gets the same sentence the check is inconclusive until `net.control_url` names a URL the tool fetches. `tool-poisoning` scans the server instructions and `serverInfo`, and `protocol` reports non-JSON-RPC output on stdout. The `sqlite` pack confirms the engine with `sqlite_version()` and says so when a server is not SQLite (DuckDB is not graded), and its file checks try the single-call, stacked and copy-into-fixture forms. The `db` pack grades a SQL tool that has another required parameter (`sql_tools[].args` fills the ones a token cannot satisfy). `git-repo-scope` probes with relative paths and judges write tools by observation, and an unjudged read tool makes it `part` at any confidence. The `fs` corpus gains array, backslash, move-through-link, dangling-link and edit-tool families, and `server.rootless: true` grades a server that takes no root argument. A correctly guarded URL tool can now be green under the `ci` profile: `effects` is `n/a` for it. See [`docs/methodology.md`](docs/methodology.md), "Round 5".
- **New in CLI 0.3.0 (still in 1.0.0): the `oauth` candidate pack.** `--oauth` starts a harness-owned stub issuer (https by default, with a throwaway CA) and fills `{issuer}`, `{jwks}`, `{audience}` and `{ca_file}` so the server under test trusts it. `oauth-token-forgery` and `oauth-claims` (critical) send forged, unsigned, expired, wrong-issuer and wrong-audience tokens after a control token is accepted; `oauth-discovery` checks the 401 challenge and RFC 9728 metadata; `oauth-scope` checks required scopes and refuses query-string tokens. Also new: `upstream-token-passthrough` (the caller's token must never reach the upstream) and `http-session-binding` (a session id is bound to the caller that opened it). Candidate checks are scored in their own pack and stay off the badge.
- **Also in CLI 0.2.2:** tool-surface drift detection (`--fail-on drift`, `sealmark diff`), a self-reported README badge (`--format badge`), `--fixture fs|git|sqlite`, and the classifier and corpus fixes for `fs`, `git`, `net` and `sqlite`.
